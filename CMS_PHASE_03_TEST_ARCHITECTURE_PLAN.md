# Фаза 3 — архитектура тестов и изоляция данных

Предпосылки: read-only аудит и фаза 2 требований согласованы. Decision log: [CMS_PHASE_02_DECISION_LOG.md](./CMS_PHASE_02_DECISION_LOG.md). Статус: **план подготовлен; тестовая архитектура не внедрялась, тесты и сервисы не запускались**.

## Цель

Подготовить безопасный, повторяемый тестовый контур для трёх независимых пакетов: корневого публичного сайта, `frontend-cms` и `backend-app`. Этот план относится только к архитектуре тестирования и изоляции, не к реализации конкретных тестов.

## План работ фазы

1. **Зафиксировать границы пакетов и команды.** Сохранить отдельный запуск unit-наборов для root/CMS/backend; явно описать, что root Playwright проверяет сайт, а не CMS; проверить конфиги и включение файлов с `.test.mjs`.
2. **Разделить уровни.** Оставить быстрые unit-тесты для доменных функций; спроектировать API/contract-набор для CMS client ↔ backend dispatcher; DB integration отдельно от mocked SQL; CMS browser tests отдельно от public-site E2E; полный publication-to-public-site путь вынести в ограниченный staging smoke.
3. **Определить DB-fixture.** Составить перечень требуемой базовой схемы и migrations, определить источник воспроизводимого baseline. Известное ограничение: migration chain дополняет существующие основные таблицы и не доказывает создание всей схемы в пустой БД. До подтверждения baseline не подключать тесты к неразличённой `DATABASE_URI`.
4. **Спроектировать изоляцию PostgreSQL.** Отдельная ephemeral DB/schema/container с отдельным тестовым URL; fail-closed guard против production/неизвестных host/db names; уникальный namespace для тестовых записей; транзакция или явный cleanup; параллельность выключена, пока нет доказанной изоляции.
5. **Спроектировать storage boundary.** Unit tests используют fake `ObjectStore`; интеграционный S3 test допускается только с отдельными тестовыми credentials и изолированным bucket/prefix, lifecycle cleanup и проверкой public URL. Никаких production buckets и реальных пользовательских файлов.
6. **Спроектировать данные и builders.** Фабрики создают минимальные связанные fixtures с уникальными slug/id и явной ролью; хранить сценарии published/draft/archived, связей медиа, change-set open/pending/returned. Не использовать существующие пользовательские записи как тестовые.
7. **Спроектировать CMS browser harness.** Отдельная Playwright-конфигурация для `frontend-cms`: тестовый backend, seed через контролируемый fixture API, чистый browser context, проверки авторизации и reload. Никаких live deployment trigger; deploy API подменять контролируемым fake либо тестовым adapter.
8. **Спроектировать публичную проверку.** Для CI проверять API revision/build marker локально с fixture API; для staging smoke использовать отдельную тестовую запись, deployment ID и content digest, затем проверить публичный DOM/URL. Запуск только после отдельного разрешения на запись в staging.
9. **Определить наблюдаемость результата.** Каждый пакет выдаёт отдельный exit code, отчёт, версии runtime/DB/browser и список skipped/flaky; в CI запрещено считать retry успешной стабильностью без отдельного flaky report.
10. **Провести threat review тестового контура.** Проверить, что секреты не печатаются, `.env` не коммитится, cleanup ограничен созданными тестом ресурсами, и любое незнакомое окружение прекращает тест до первой записи.

## Результаты, необходимые для завершения фазы 3

- схема уровней и независимые команды для трёх пакетов;
- подтверждённый способ создавать/сбрасывать тестовую PostgreSQL БД на известной базовой схеме;
- зафиксированные запреты и fail-closed условия для production URL/credentials;
- безопасный storage fake и отдельный план изолированного S3-интеграционного контура;
- builders/fixtures contract с уникальными данными и гарантированным cleanup;
- план CMS browser harness и ограничений deployment trigger;
- список проверок, требующих отдельного допуска (staging write, S3 test bucket, deployment smoke).

## Блокеры

- Нет подтверждённого способа получить полный базовый schema bootstrap для пустой PostgreSQL базы.
- Нет проверки текущих env и сервисов; тестовые DB/S3 не создавались и не выбирались.
- Нельзя запускать интеграционные или E2E сценарии до доказательства, что они не используют рабочую БД, реальное media bucket или production deploy credentials.
- Пользовательский контракт удаления используемого файла расходится с текущим backend/UI и потребует отдельной реализации после согласования плана исправления.

## Граница допуска

После согласования этой фазы можно подготовить отдельный план фазы 4 (кандидаты на переписывание/устаревшие тесты). Создание/изменение test harness, добавление тестов и запуск команд остаются отдельной работой и требуют отдельного плана/разрешения согласно исходной миссии.
