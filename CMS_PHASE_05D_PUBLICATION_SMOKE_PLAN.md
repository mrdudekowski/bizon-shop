# Фаза 5D — staging publication smoke

Дата: 2026-10-08
Статус: **частично выполнена; публикационный сценарий остановлен из-за несоответствий текущего staging UI ожидаемому workflow**.

## Цель

На staging проверить путь «создание → сохранение → независимое чтение → публикация → проверка точной ревизии и публичной страницы». Работать только с уникальными QA данными, а после сценария удалить тестовые данные и подтвердить cleanup.

## План проверки

1. Убедиться, что открыт админский интерфейс staging и проверить разделы без изменения существующих записей.
2. Создать одну временную статью с уникальными QA title/slug.
3. Проверить запись в CMS после перехода и нового чтения; сверить только собственный QA объект в БД.
4. Проверить статус черновика, очередь согласования, публикацию и публичный DOM; сопоставить результат с публичным `content-revision.json`.
5. Проверить библиотеку файлов read-only: список использований, предупреждение, индикатор и доступность удаления используемого файла. Не удалять существующие объекты.
6. Удалить только созданный QA объект и подтвердить отсутствие строки после повторного чтения.

## Границы безопасности

- Пользователь подтвердил, что открытые CMS и БД являются staging, и разрешил создавать/удалять тестовый контент и запускать публикацию.
- Не читать записи, пароли, сессии или иные пользовательские данные. DB readback ограничивать уникальным QA маркером.
- Не трогать существующие страницы, товары, медиа, историю и миграции.
- Интеграционные тесты фазы 5C требуют отдельной disposable PostgreSQL базы; staging DB не считать такой базой.

## Фактическое выполнение

- В CMS открыт интерфейс администратора; видны страницы, материалы, файлы, публикации и пользователи. В очереди «На одобрении» заявок нет.
- В разделе «Материалы» при создании введены уникальные title `QA-20261008-5D-01A11753` и slug `qa-20261008-5d-01a11753`. Форма перешла на `/materials/editor?id=article-14`, но редактор оставался на «Загружаем данные…».
- Независимый запрос в Adminer подтвердил ровно одну строку с этим уникальным title в `tire_iq_articles`, со статусом `draft`. Свежая вкладка CMS показывала пустой список материалов, запись в списке не находилась.
- По разрешению пользователя тестовая строка была удалена точечным условием по `id=14`, точным title, slug и `status='draft'`. Последующий read-only count по тем же значениям подтвердил 0 остаточных строк. Ни тестовая запись, ни файл не публиковались.
- В библиотеке файлов отображаются 39 объектов. Для используемых файлов показаны места использования и кнопка «Удалить» отключена. На видимых карточках отдельного зелёного светящегося индикатора нет. Существующие файлы не менялись.
- Открытие `/content-revision.json` на том же сайте отдало оболочку приложения BIZON, а не JSON marker; точную публичную ревизию подтвердить не удалось.
- Прямая перезагрузка вложенных URL возвращала главный экран вместо соответствующего CMS раздела/редактора. Переход из навигации позволял открывать некоторые списки, но запись материала и редактор не удалось проверить через устойчивый UI.

## Вывод и оставшиеся проверки

Staging smoke не пройден. Основные блокеры: редактор созданного материала зависает и список не отражает сохранённый draft; deep-link/reload не восстанавливает вложенные маршруты; публичный revision marker недоступен; медиабиблиотека не соответствует согласованному UX удаления используемого файла. Это может означать, что на staging развернута версия, отличающаяся от локальных изменений фаз 6–7.

До повторного прогона нужно развернуть актуальный build приложения на подтверждённый staging, исправить/проверить загрузку материала и маршрутизацию, обеспечить отдачу `content-revision.json`, затем повторить полный сценарий с тестовым редактором и администратором. Фаза 5C остаётся отдельной: нужен disposable PostgreSQL с утверждённым schema baseline.

## Дополнение после завершения QA-очистки и проверки автосборки — 2026-10-08

- Пользователь подтвердил окончательное удаление QA-записи `article-15` (`qa-5d-20261008-b5440a5-01a11753`). Запись удалена через CMS. Точечный read-only запрос Adminer по `id=15` и этому уникальному slug вернул «Нет записей».
- После удаления публичный `GET https://mrdudekowski-bizon-shop-593a.twc1.net/v1/articles/qa-5d-20261008-b5440a5-01a11753` вернул HTTP 404 и `{"ok":false}`.
- Проверен фактически запущенный backend app `266233`: успешный деплой `6b8c3d9`, тот же коммит, в котором присутствует автодеплой-код `triggerStaticSiteDeploy`.
- Код сообщает «не настроено», если в окружении backend отсутствует `TIMEWEB_CLOUD_TOKEN` или `TIMEWEB_PUBLIC_SITE_APP_ID`. В панели Timeweb среди переменных приложения видны `NODE_ENV`, `S3_*`, `DATABASE_URI`, `CMS_*` и `CORS_ALLOWED_ORIGINS`; оба имени `TIMEWEB_*` отсутствуют. Значения секретов не раскрывались.
- Поэтому подтверждённая причина отсутствия автосборки — неполная конфигурация окружения backend, а не отсутствие интеграционного кода или сбой CMS. Автосборка требует задать секрет `TIMEWEB_CLOUD_TOKEN` и ID Front-приложения `TIMEWEB_PUBLIC_SITE_APP_ID=266061`, затем перезапустить backend и выполнить публикацию/повтор сборки. Для создания секрета нужен токен владельца Timeweb; его значение в текущем контексте недоступно.
- Статические файлы Front и публичный DOM после публикации всё ещё не проверены. Этот статус не меняется от проверки API: HTTP 404 подтверждает удаление записи из backend, но не проверяет наличие/отсутствие уже сгенерированных файлов на статическом Front.
