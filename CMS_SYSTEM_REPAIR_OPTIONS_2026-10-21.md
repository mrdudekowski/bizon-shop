# Варианты системного исправления проблем CMS

**Дата:** 21 октября 2026 г.<br>
**Основа:** read-only E2E аудит боевой CMS и сверка обнаруженных симптомов с кодом CMS/backend и публичного сайта.<br>
**Назначение:** выбрать устойчивые решения и разбить работу на проверяемые этапы. Это предложения, а не разрешение на изменения.

## Краткий вывод

Подтверждённые проблемы сосредоточены в четырёх местах: контракт URL медиа между системами; валидация содержимого загружаемого файла; доставка актуальной сборки CMS в production; дублирование правил склонения в CMS и публичном сайте. Для них не требуется переписывать систему целиком. Нужны явные межсервисные контракты, общий путь данных и проверки на настоящих границах API, хранилища и production-сборки.

Пятая наблюдаемая проблема — редактор каталога сразу показывает несохранённые изменения. Код объясняет её автоматической нормализацией черновика, но не доказывает, что это нежелательное поведение: это продуктовый выбор, который следует решить до реализации.

Аудит не выявил подтверждённых P0/P1. Ни один вариант ниже не предлагает исправлять отдельное имя файла, пришивать URL к записи, выполнять немедленную очистку S3/БД или перестраивать всё приложение. Причина отсутствия галереи именно в production пока не установлена: подтверждено расхождение production-интерфейса с доступным исходным кодом, но не конкретная причина деплоя.

## Подтверждённые проблемы и пути решения

### 1. Разные экраны по-разному разрешают URL изображений

**Серьёзность:** P2, ограниченная проблема интерфейса и контракта данных.<br>
**Что проверено:** 6 записей используют пути `/images/premium/...`; на origin CMS такие URL отвечают HTML, а не изображением. Четыре записи используются в контенте. Файлы существуют в `public/images/premium` основного сайта. API выдаёт URL в поле `dataUrl`, хотя это поле может содержать URL или путь, а не data URI. В части CMS применяется `resolveMediaPreviewUrl()`, в частности в `PlacementFields` и `CatalogRow`; `MediaLibrary`, `MediaPicker`, `TireModelList` и draft-diff содержат прямое отображение URL. Поэтому одинаковая запись может отображаться по-разному в разных компонентах. Это доказывает проблему CMS preview/origin-контракта, но не поломку изображения на публичном сайте.

**Глубина:** средняя. Источник — размытая семантика общего поля и неоднородное использование resolver-а, а не неверная модель хранения всех данных.

**Варианты:**

1. **Минимальный ремонт:** применить существующий resolver во всех CMS превью. Плюс: малый объём. Минус: каждый потребитель должен помнить об этом; поле `dataUrl` остаётся неоднозначным, а другие клиенты могут ошибиться снова.
2. **Явный resolver-контракт CMS:** ввести один общий CMS-модуль для преобразования относительного пути в origin публичного сайта и использовать его во всех превью. Плюс: выравнивает экраны без изменения формата API и БД. Минус: CMS остаётся владельцем адресации публичных ресурсов, нужно правильно задать origin для каждой среды.
3. **Канонический контракт медиа (рекомендуется):** определить семантику полей медиа на границе API. Различать стабильный публичный URL/путь и URL объекта хранилища, не называть произвольные значения `dataUrl`; централизовать разрешение/построение URL в одном общем слое. API, CMS и публичный сайт используют договорённый формат, а не локальные строковые догадки. Сохранить совместимое чтение старых URL на время перехода.

**Рекомендация:** вариант 3, но узким этапом: сначала инвентаризировать реальные типы значений и всех потребителей; зафиксировать схему/семантику; затем подключить единый resolver на чтении; только после проверки отдельно решить, нужна ли миграция старых записей. Не менять уже используемые URL массово без контрольной выборки.

**Критерии готовности:** относительный путь сайта, абсолютный URL S3 и отсутствующее значение обрабатываются предсказуемо; один и тот же объект имеет одинаковый preview в библиотеке, picker, редакторах, списках и diff; CMS не пытается показать страницу HTML как картинку; проверено, что публичное отображение сохраняет прежнее поведение.

### 2. Backend принимает неполные изображения как валидные файлы

**Серьёзность:** P2, дефект целостности медиа.<br>
**Что проверено:** один неиспользуемый S3 PNG возвращает HTTP 200 и `image/png`, но содержит лишь 16 байт — сигнатуру и неполный заголовок; он не декодируется. `putMedia.ts` проверяет размер и тип/сигнатуру, но не полноценную структуру изображения. Такой подход может пропустить усечённые данные. Этот объект неиспользуемый, поэтому подтверждённого воздействия на публичную страницу нет; он не доказывает причину прежней ошибки загрузки карусели.

**Глубина:** локальная валидация на серверной границе загрузки. Схема БД сама по себе не может гарантировать декодируемость байтов.

**Варианты:**

1. **Минимальный ремонт:** проверять размер, разрешённый MIME и корректность полного формата имеющимся безопасным image decoder до регистрации медиа.
2. **Полный жизненный цикл upload (рекомендуется):** сервер валидирует и декодирует изображение; рассчитывает контрольную сумму; сохраняет объект; подтверждает его размер/метаданные; только после этого фиксирует ссылку в БД. При ошибке сохраняет согласованность: временный объект удаляется/не становится видимым, а запись медиа не считается успешной. Повторная отправка не создаёт случайные дубли.
3. **Глубокая замена медиаподсистемы:** перепроектировать хранилище и ingestion pipeline вокруг очереди/карантина и фоновой обработки. Это оправдано только при подтверждённой потребности в больших объёмах, преобразованиях или асинхронной обработке; текущие данные такой необходимости не показывают.

**Рекомендация:** вариант 2 с текущими компонентами системы. Сначала контракт и проверки, затем тесты на валидные файлы, обрезанные заголовки, неверное содержимое с PNG MIME, превышение лимита, сбой S3 и сбой сохранения metadata. Не расширять список форматов без необходимости.

**Отдельная работа с найденной записью:** проверить историю и metadata объекта `test.png`, выяснить, откуда появились 16 байт. После подтверждения использования и соответствия DB/S3 — принять отдельное решение о замене или удалении. Сейчас не удалять объект и запись автоматически.

**Критерии готовности:** усечённый/нечитаемый файл отклоняется до появления успешно загруженной записи; валидный файл после загрузки читается из S3 и открывается после перезагрузки редактора; сбои хранения не оставляют ложную запись «загружено»; проверена фактическая повторная загрузка в изолированной среде.

### 3. В production CMS нет кнопки выбора изображения из галереи

**Серьёзность:** P2, доступность функции в production.<br>
**Что проверено:** в production проверены поля карусели магазина, плиток категории и Hero главной страницы — кнопки выбора из галереи нет. Доступные локальная ветка и origin CMS содержат реализацию `MediaPicker` и тесты. Страница приложения Timeweb, доступная при проверке, показывает revision backend и не устанавливает, какой репозиторий/ветка/сборка CMS обслуживает интерфейс. Следовательно, расхождение доказано, но точная причина (целевой проект, ветка, команда сборки, деплой, кэш либо иной артефакт) не установлена.

**Глубина:** неизвестна до трассировки deployment chain; скорее всего release/configuration, а не отсутствие реализации. Не следует сейчас угадывать причину или добавлять условие показа кнопки: исходный компонент показывает picker без видимого feature gate.

**Варианты:**

1. **Повторно развернуть предполагаемый CMS проект:** быстро, но риск развернуть не тот репозиторий или продолжать скрывать источник проблемы.
2. **Восстановить проверяемую цепочку релиза (рекомендуется):** определить домен → конкретное приложение/проект CMS → репозиторий и ветку → сборочную команду/переменные → artifact/build ID и commit SHA → фактически отданные браузеру ресурсы. Затем выровнять target с утверждённой веткой и развернуть проверенный artifact.
3. **Перевести CMS UI на другую схему доставки:** рассматривать только если текущая платформа не способна связывать артефакт с исходным commit или надёжно инвалидировать старые сборки. Это отдельная архитектурная задача; аудит не подтверждает, что она нужна.

**Рекомендация:** вариант 2. Сначала read-only определить фактический target и deployed artifact. Если target верен, выяснить: не запускался ли деплой; если bundle свежий — не кэшируется ли старый HTML/JS; если код расходится — не настроен ли другой source/branch/build path. Проверять feature gate только если deployment/runtime config обнаружит его. Не выполнять новый production deploy в рамках этого документа.

**Критерии готовности:** известны CMS deployment target и commit SHA; production bundle соответствует ожидаемому commit; picker виден во всех проверенных типах image field; выбранное неиспользуемое медиа корректно сохраняется и отображается после reload; загрузка нового файла продолжает работать.

### 4. Неверное склонение количества товаров

**Серьёзность:** P2, подтверждённая ошибка подписи интерфейса.<br>
**Что проверено:** production показывает `1 товаров`; `ShopProductList.tsx` использует фиксированный суффикс. Похожий фиксированный текст есть внизу `ShopCategoryProducts.tsx`. Публичный сайт уже использует `shopProductCountLabel()` с правилами русского склонения. Счётчик равен 1, значит проблема в отображении, не в данных.

**Глубина:** небольшая, но причина системная — дублированные правила представления в отдельно собираемых приложениях.

**Варианты:**

1. **Минимальный локальный фикс:** корректно форматировать окончания в двух CMS местах. Быстро, но логика может вновь разойтись.
2. **Один переиспользуемый форматтер (рекомендуется):** вынести небольшую чистую функцию в общий контракт/пакет, доступный обоим приложениям, или синхронизировать одинаково покрытый модуль, если общий пакет нарушил бы границы сборки. Использовать во всех местах CMS и публичного сайта.
3. **Полная локализационная архитектура:** каталог сообщений и ICU plural rules для всех текстов. Не требуется для одного обнаруженного счётчика; пересматривать только если есть более широкая задача локализации.

**Рекомендация:** вариант 2. Проверить все count labels в обоих проектах, не только найденные два; покрыть числа 0, 1, 2, 4, 5, 11, 21 и 22.

**Критерии готовности:** одинаковые подписи на CMS и публичном сайте для одного количества; проверены края правила; данные счётчика не изменяются.

### 5. Редактор каталога показывает dirty state сразу после открытия

**Серьёзность:** не подтверждённый дефект; требуется решение о продуктовой семантике.<br>
**Что проверено:** `mergeCategories()` добавляет отсутствующие в сохранённом `shop-home.catalog.tiles` категории во временный draft. Сравнение нормализованного draft с сохранённым snapshot выставляет признак несохранённых изменений сразу. В аудитной сессии сохранения не делали, а код объясняет предупреждение без скрытого запроса на запись.

**Глубина:** решение о source-of-truth для каталоговых tiles. Сам dirty indicator ведёт себя согласно текущему сравнению, но само сравнение смешивает нормализацию при чтении и редактирование пользователем.

**Варианты:**

1. **Производные tiles (рекомендуется, если все категории должны автоматически попадать в витрину):** категории — источник существования плиток, а в CMS сохраняются только пользовательские настройки/переопределения. Начальное объединение — derived view, поэтому открытие не dirty.
2. **Явное snapshot-поведение:** tiles — отдельный сохраняемый список; появление новой категории не меняет опубликованный список без решения редактора. Тогда UI должен отличать предложенную синхронизацию от правки пользователя и предлагать ясное действие «добавить новые категории», с preview до сохранения.
3. **Однократная миграция данных:** нормализовать существующие записи явной миграцией с отчётом о разнице и планом возврата. Это применимо только если бизнес-правило уже утверждено и данные действительно должны перейти в новое представление; не маскировать миграцию автосохранением страницы.

**Рекомендация:** сначала согласовать ожидаемое поведение для новой категории, переименованной/скрытой категории и сохранённых визуальных overrides. Если все категории должны публиковаться автоматически — вариант 1. Если нет — вариант 2. Вариант 3 не выбирать до этих ответов.

**Критерии готовности:** после открытия неизменённого редактора статус чистый либо показано отдельное объяснимое действие синхронизации; GET не записывает изменения; добавление/переименование/деактивация категории сохраняет утверждённое правило и не теряет ручные настройки.

## Что не предлагается исправлять как найденную поломку

- 12-часовой срок admin-сессии подтверждён исходным кодом и может объяснять переход к login после длительной работы. Аудит не устанавливает проблему с логином; менять TTL следует только при продуктовой потребности и с оценкой сессий/безопасности.
- Ноль моделей OTR, два активных пользователя из четырёх, пустые SEO поля и отсутствие изображения у одной категории не признаны ошибками: нет авторитетного требования, с которым можно их сравнить.
- Для старых путей `/images/premium/...` не доказан сбой публичной страницы; установлен только ответ HTML на origin CMS.
- Усечённый `test.png` не доказывает, что именно он вызвал прежнюю ошибку загрузки карусели.

## Архитектурные альтернативы для всей системы

| Подход | Что меняется | Сильные стороны | Цена/риск | Оценка |
|---|---|---|---|---|
| Локальные точечные правки | Каждый найденный экран/валидатор исправляется отдельно | Минимальный diff, быстрая поставка | Повторение логики и контрактная неоднозначность остаются | Подходит только как временная стабилизация |
| Общие контракты на границах (рекомендуется) | Единая семантика media URL, общая validation boundary, общий count formatter, проверяемый build identity | Устраняет конкретные причины, небольшие этапы, совместимый переход | Нужны владельцы контрактов и проверка всех consumers | Лучший баланс для текущих доказательств |
| Большая замена платформы/медиапайплайна | Новый storage/UI/release architecture | Может упростить будущие масштабы и workflow | Высокий объём, миграции и новые риски; текущий аудит не обосновывает | Не начинать без дополнительных измерений/требований |

**Рекомендуемый вектор:** общие контракты на границах, с совместимым чтением старых данных и малым количеством явно проверяемых изменений. Большое переписывание не является необходимым следствием обнаруженных дефектов.

## План работ небольшими этапами

### Этап 0 — закрыть неизвестные deployment/runtime факты (только чтение)

1. Установить CMS-specific deployment target и точную цепочку источника/сборки/доставки.
2. Получить реальный CMS commit/build ID и сопоставить его с веткой, содержащей picker.
3. Составить инвентарь форматов `media.url`, фактических origins и потребителей в API, CMS и публичном сайте.
4. Проверить DB/S3 metadata и происхождение усечённого объекта, не изменяя их.

**Выход:** короткий evidence report, точный список affected consumers и подтверждённая гипотеза для отсутствующего production picker.

### Этап 1 — сформировать контракты и зафиксировать пользовательское поведение

1. Утвердить семантику публичного пути, S3 URL и image preview URL.
2. Утвердить upload lifecycle и требования к успешной валидации.
3. Решить, являются ли tiles производными от категорий или отдельным snapshot.
4. Определить, какой общий package/boundary допустим для чистого count formatter при раздельной сборке CMS и сайта.

**Выход:** небольшие acceptance criteria для каждого из 4 направлений и выбранное правило каталога.

### Этап 2 — local isolated tests

1. Подготовить disposable PostgreSQL и изолированное object storage/emulator с явной конфигурацией, исключающей production endpoint/credentials.
2. Поднять CMS + API в этой среде и пройти сценарии входа, навигации, upload/select, save/reload, publication, чтения медиа.
3. Добавить точечные API/UI tests для URL resolver, некорректных изображений, общего count formatter и tile dirty-state.

**Выход:** повторяемый E2E прогон, показывающий и UI, и сохранение/повторное чтение; существующие unit tests остаются полезными, но не выдаются за proof persistence.

### Этап 3 — независимые исправления в порядке риска

1. Выпустить backend image integrity validation с тестами отказа/успеха.
2. Унифицировать медиа URL чтение в CMS и проверить public consumer contract.
3. Устранить расхождение production CMS artifact после определения правильного target.
4. Устранить дублирование count formatting.
5. Реализовать выбранное правило каталога, если аудит продукта подтвердит, что текущее поведение нежелательно.

**Зависимости:** deployment issue можно независимо диагностировать на этапе 0; release допускается только после подтверждённого target. Миграция данных не блокирует resolver на чтении и не должна идти раньше инвентаря.

### Этап 4 — staging и production proof

1. Проверить candidate build в staging с безопасной тестовой записью и удалением только тестового объекта.
2. Проверить upload → S3 read → metadata → select → save → reload → public rendering.
3. В production сначала проверить build identity и UI. Запись/загрузка/удаление в production — отдельные действия только после согласованной тестовой методики.
4. Сравнить старые URL и новое представление на контрольной выборке перед любым массовым изменением данных.

## Приоритет и рекомендуемый порядок

| Порядок | Работа | Почему |
|---|---|---|
| 1 | Установить production CMS build/source и причину отсутствия picker | Устраняет неизвестность релиза и может вернуть уже реализованную функцию без нового кода |

## Безопасные границы

- Этот документ основан на read-only аудите. Изменений кода, CMS, backend, БД, S3 и Timeweb deployment при его подготовке не выполнялось.
- До выбранного и проверенного дизайна не запускать production миграцию, не удалять/перезаписывать объект, не менять auth TTL и не делать production deploy.
- До локального E2E использовать только явно изолированные DB/storage credentials; запуск backend с неизвестным `.env` не считать безопасным.
- Любая миграция должна иметь dry-run отчёт, проверку количества затрагиваемых записей, backup/rollback plan и повторную проверку после применения.
- Не исправлять конкретные записи хардкодом: правка должна устранять правило, которое породило класс ошибки.

## Решения, требуемые перед реализацией

1. Подтвердить рекомендуемый общий подход: исправлять контракты на границах без полной замены стека.
2. Для плиток магазина выбрать: автоматически следовать списку категорий или сохранять редакторский snapshot.
3. После отдельной read-only проверки storage решить судьбу повреждённого неиспользуемого `test.png`.
4. Утвердить отдельный план staging/prod проверки после подготовки изолированной E2E среды.

После выбора решений работу следует разделить на независимые спецификации/PR, чтобы backend validation, media URL contract, release chain и presentation logic можно было проверить и выпускать без смешения миграций и UI.
