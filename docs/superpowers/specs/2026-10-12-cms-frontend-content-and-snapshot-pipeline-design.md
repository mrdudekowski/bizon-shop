# Bizon CMS, Frontend и автономный снимок контента

## Цель

Сделать CMS единственным источником опубликованного редакционного контента публичного сайта Bizon: текстов, фотографий, смысловых иконок, alt-текстов, подписей, CTA, ссылок и порядка секций. Frontend отображает опубликованную версию. При отказе backend/API, PostgreSQL или S3 публичные страницы продолжают показывать последний целостный снимок контента вместе с необходимыми медиа.

CMS управляет содержанием и выбором разрешённых блоков. Код остаётся владельцем поведения компонентов, маршрутизации, адаптивной сетки, интерактивности и валидации. Системная айдентика и поведение компонентов остаются в коде, если отдельное редакторское управление ими не требуется.

## Основание и текущий baseline

Аудит выполнен в каноническом checkout `Bizon-main-app`, ветка `main-app`; состояние проверено 2026-10-12. Исследованы исходники, локальные опубликованные API и SSR HTML публичных страниц.

- Локальные сервисы: сайт `127.0.0.1:3000`, CMS `127.0.0.1:3001`, backend `127.0.0.1:4000`, PostgreSQL `127.0.0.1:5433/bizon`.
- Локальная БД публикует один тип дисков и четыре модели. У каждой модели есть основное изображение и галерея из трёх изображений. Два проверенных URL медиа дисков ответили `200 image/png`.
- У пяти опубликованных Shop-категорий изображения есть у четырёх. Ответ `shop-home` не содержит hero-изображения и слайдов, поэтому сайт использует дефолты из исходников.
- `/v1/pages/home` не возвращает заполненные изображения hero и кампании Shop; на публичной главной фактически отображаются локальные дефолты.
- `/v1/pages/about`, `/branding`, `/warranty` и `/become-a-supplier` возвращают `404`; соответствующие публичные маршруты показывают текст и фото из кода.
- Кампания брендинга главной использует статические изображения сравнения и статические тексты/подписи/CTA. Блок экспертизы использует статические фото, alt-текст и CTA.
- CMS хранит `selectionEntry`, backend читает его, но активная главная `src/app/(site)/page.tsx` не отображает это поле.
- `src/constants/images.ts` содержит fallback-карту по slug, а `src/lib/content/pages/merge.ts` подставляет кодовые дефолты при пустых значениях.
- Существует проверка content revision при статической сборке и публикации. Она подтверждает согласованность версии опубликованных данных, но сама по себе не доказывает наличие независимой копии файлов медиа или ежедневного снимка.

Это локальный baseline, а не подтверждение production-состояния.

## Рассмотренные подходы

### 1. Отдельные фиксированные поля для каждой страницы

Простой интерфейс и строгая схема, но таблицы и формы разрастаются при добавлении повторяющихся секций.

### 2. Свободный конструктор произвольных блоков

Максимальная гибкость, но редактор может собрать визуально или функционально некорректную страницу; потребуются сложная валидация и большой объём UI.

### 3. Типизированные блоки с ограниченным набором вариантов — выбранный подход

Страница состоит из поддерживаемых Bizon-блоков с явными полями и порядком. Редактор управляет содержанием и последовательностью, а код контролирует допустимую структуру и поведение. Карточки, слайды и галереи остаются типизированными коллекциями. CMS не принимает произвольный HTML/JS или произвольные имена компонентов.

## Архитектурные правила

### Источник контента

1. Опубликованные CMS-данные — источник истины для редакционного контента.
2. Черновики доступны только CMS и не попадают в публичный API или снимок.
3. Для каждого поля задаётся семантика: обязательное, необязательное или декоративное. Пустое значение не должно молча подменяться старым редакционным контентом.
4. Один media asset можно использовать в нескольких местах. Alt-текст, фокус кадра и параметры конкретного размещения принадлежат размещению в блоке.
5. CMS хранит media ID; backend разрешает опубликованные URL. Публичные компоненты не получают доступ к PostgreSQL или S3-секретам.

### Типы ассетов

- **Редакционные фотографии и иллюстрации:** выбираются из Media Library и связываются с блоком CMS.
- **Смысловые иконки и диаграммы:** редактируются через CMS, если их содержание должно меняться редактором. Интерактивные технические схемы можно оставить в коде, если они описывают фиксированное поведение.
- **Системные UI-ассеты:** навигационные логотипы, стрелки, системные пиктограммы и декоративные SVG остаются в дизайн-системе, если не принято отдельное решение управлять ими из CMS.
- **Placeholder:** нейтральное состояние только для явно необязательного изображения; не заменяет обязательное опубликованное фото.
- **Fallback:** переходный механизм миграции. Редакционные fallback удаляются после заполнения CMS и появления проверенного снимка.

### Версия снимка

Снимок содержит:

- `schemaVersion` — версию формата;
- `contentRevision` — ревизию опубликованных read models;
- `snapshotRevision` — digest нормализованного manifest данных и хешей медиа;
- `generatedAt`, список включённых маршрутов/сущностей и результат проверок;
- опубликованные JSON read models;
- локальные копии всех используемых медиа;
- media manifest: ID, локальный путь, MIME type, размер и SHA-256.

Секреты, данные аккаунтов CMS, черновики, административные поля, токены и персональные данные не включаются в публичный снимок.

## Пайплайн публикации и снимка

1. Редактор сохраняет изменения как draft.
2. CMS валидирует обязательные поля, типы блоков, ссылки, изображения, alt-тексты и права публикации.
3. Backend атомарно публикует страницу и связанные коллекции; публичный слой не видит частично опубликованный draft.
4. Backend фиксирует `contentRevision` опубликованного набора.
5. Сборщик снимка читает согласованный опубликованный набор, строит manifest и получает используемые файлы из S3.
6. Сборщик проверяет маршруты, связи, локальные пути, MIME type, размер, контрольные суммы и отсутствие обязательных медиа.
7. Новая версия собирается отдельно. Только полная проверка разрешает атомарно активировать новую версию сайта/снимка.
8. Обновление запускается после публикации; ежедневный запуск служит сверкой и восстановлением пропущенного запуска.
9. Предыдущая проверенная версия остаётся доступной для отката. Ошибка генерации, чтения S3 или деплоя не заменяет её.
10. CMS показывает отдельно: публикация в БД, готовность снимка, подтверждение публичной версии. Ответ API или провайдера сам по себе не означает, что публичный сайт обновлён.

Текущая проверка content revision сохраняется и дополняется проверкой медиа manifest. Ревизии БД недостаточно, если байты медиа могут измениться независимо от записи.

## Поведение при отказах

| Состояние | Требуемое поведение публичного сайта |
|---|---|
| Backend/API доступен | Используется опубликованная версия; сборочный артефакт содержит тот же проверенный revision. |
| Backend/API недоступен | Отдаётся последний активированный снимок. |
| PostgreSQL недоступен | Публичный рендер не требует обязательного чтения БД и использует снимок. |
| S3 недоступен | Страницы используют локально включённые медиа. Новая версия не активируется без обязательных файлов. |
| API, БД и S3 одновременно недоступны | Показывается последняя проверенная версия контента и медиа. |
| Снимок неполон или revision меняется во время чтения | Новая версия отклоняется; предыдущая продолжает работать. |
| Нет подходящего снимка | Показывается явное ограниченное состояние ошибки, без имитации актуального контента. |

Снимок покрывает публичное чтение контента и каталога в рамках включённых read models. Он не обещает офлайн-работу операций записи/реального времени: входа в CMS, заказов и корзины, отправки форм, подтверждения наличия и цены. Их деградированный режим определяется отдельно.

## CMS-интерфейс и иерархия

- Иерархия CMS: **страницы → секции → элементы/материалы → медиа**.
- Редактор видит превью размещения, alt-текст, фокус кадра и места использования ассета.
- В одном редакторе блока находятся изображение, заголовок, текст, подпись, CTA, URL и мобильный вариант.
- Повторяющиеся секции можно добавлять, удалять и переставлять; набор типов ограничен поддерживаемыми шаблонами.
- До публикации показываются ошибки и предупреждения. Пустое обязательное изображение или битая ссылка блокируют публикацию.
- Draft/published и статус публичного снимка отображаются отдельно.

## Поэтапная реализация

### Срез A — реестр и контракт

Составить карту активных маршрутов, блоков и ассетов. Для каждого указать компонент, CMS-поле, backend/DB relation, fallback, связанные тексты и ожидаемое поведение снимка. Сверить опубликованные read models и покрытие content revision.

### Срез B — главная

Использовать `2026-10-12-homepage-content-cms-design.md` как отдельный scoped slice. Перенести текущие изображения в начальные CMS-размещения; связать branding и expertise с CMS; подключить `selectionEntry` или удалить неиспользуемое поле после согласования.

### Срез C — контентные страницы и Shop

Расширить CMS-управление контентными страницами за пределы hero/SEO. Перенести lifestyle-категории и истории автомобилей Shop в типизированные блоки. Не дублировать каталог. До миграции сверить slug `accessory` и `accessories`.

### Срез D — контентные изображения каталога

Сохранить CMS-связи основных изображений и галерей моделей/типов/товаров. Превратить slug-fallback в явные переходные данные и убрать после загрузки ассетов в CMS. Системные UI-иконки оставить в коде; смысловые контентные иконки включить в реестр CMS-размещений.

### Срез E — снимок с медиа

Реализовать генерацию manifest, локальное включение байтов медиа, запуск после публикации и ежедневно, atomic promotion, хранение предыдущей рабочей версии и rollback. Подтвердить доступность снимка независимо от API/БД/S3 в runtime публичного сайта.

### Срез F — удаление редакционного хардкода и приёмка

Удалять fallback только после заполнения CMS и подтверждения нового публичного снимка. Проверить сохранение, публикацию, повторное чтение CMS, публичное отображение и каждый режим отказа. Результаты разделять по source, API/DB, snapshot artifact, локальному runtime и публичной поверхности.

## Критерии готовности

1. Каждое контентное изображение и связанный текст выбранных маршрутов имеют поле CMS и выводятся из опубликованных данных.
2. Смысловые иконки, alt-тексты, подписи, порядок и CTA управляются соответствующим CMS-блоком; для остающихся в коде дизайн-системных иконок есть явная причина.
3. Изменение CMS подтверждено повторным чтением и публичным HTML/браузером.
4. Артефакт содержит опубликованные read models и все необходимые медиа; manifest проходит проверки схемы и хешей.
5. Отказ API, БД или S3 не портит активный снимок.
6. Неудачная публикация/сборка не активирует частичную версию.
7. Предыдущую версию можно восстановить без исходных API/БД/S3.
8. Операции записи и реального времени явно отделены от гарантий контентного снимка.
9. Production migrations, записи, публикации и deploy выполняются только по отдельному запросу и после production-specific review.

## Не входит в этот дизайн

- Перенос поведения, маршрутизации, адаптивной сетки или бизнес-логики в CMS.
- Свободный HTML/JS-конструктор.
- Офлайн-операции CMS, заказы, формы, авторизация и гарантированно актуальные складские данные.
- Изменение production-данных, production migration или немедленный deploy.
- Перенос системной айдентики в CMS без отдельного UX-решения.

## Риски и вопросы для implementation plan

- Размер артефакта и дублирование оригиналов медиа: определить renditions, форматы и лимиты.
- Подтвердить для текущего Timeweb runtime атомарное переключение и хранение предыдущих deploy/snapshot.
- Проверить схему и незакоммиченные CMS-изменения перед выбором миграций; не перезаписывать их.
- Отдельно описать границу Content API в production: статический build и локальный dev имеют разные границы отказа.
- Определить retention после оценки размера/стоимости, сохранив как минимум предыдущую рабочую версию.

## Самопроверка спецификации

- Определены цель и границы CMS, Frontend и снимка.
- Типизированные блоки не превращаются в произвольный page builder.
- Снимок включает байты медиа, а не только URL.
- Отказы API, PostgreSQL и S3 разделены; офлайн-операции записи исключены.
- Этапы упорядочены по зависимостям; production-изменения исключены.
- Существующие homepage CMS и static content revision specs остаются scoped-документами; их контракты согласуются перед implementation plan.
