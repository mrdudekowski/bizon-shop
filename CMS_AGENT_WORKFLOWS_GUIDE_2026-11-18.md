# Практическое руководство: надежная разработка CMS и работа с агентами

Руководство опирается на аудит Bizon от 18 ноября 2026 года. Там, где у CMS есть подходящий пример, использую его. Вымышленные примеры явно отмечаю.

## 1. Смотрите на путь данных целиком

CMS — интерфейс над бизнес-процессом. Для страницы путь выглядит так:

~~~text
CMS форма
  → admin API
  → проверка сессии и прав
  → backend операция
  → транзакция PostgreSQL
  → published snapshot и revision
  → статическая сборка/обновление
  → публичная страница
~~~

Успешный ответ публикации не доказывает, что публичная страница обновилась: backend может сохранить данные и отдельно запустить deploy. Проверяйте каждый переход, чтобы найти первое место, где значение потерялось.

Для CMS это означает сравнить: значение формы, запрос браузера, ответ backend, независимое чтение из БД, ответ published API, revision сборки и HTML публичного маршрута. У каждого слоя свое состояние и возможный отказ.

### Сквозной вымышленный пример: портал «Север»

Чтобы показать принципы для интеграций, которых нет в проверенной CMS, представим сайт «Север»: CMS управляет страницами «О компании», «Услуги», «База знаний» и «Контакты»; backend API работает с PostgreSQL; фронтенд отдает статические страницы и виджеты; виджеты показывают карту офисов и форму записи; backend отправляет заявки во внешнюю CRM.

Путь формы записи: виджет → backend validation → сохранение заявки в PostgreSQL → очередь/outbox → CRM API. Фронтенд не получает CRM-секрет и не вызывает CRM напрямую. Если CRM временно недоступна, заявка остается сохраненной, а фоновая отправка повторяется с ограничением и наблюдаемым статусом. Тесты отдельно покрывают валидацию, сохранение, повторную отправку и пользовательское сообщение.

Этот пример вымышлен и используется только для иллюстрации интеграции внешнего сервиса; он не описывает фактическую архитектуру Bizon.

## 2. Разделяйте факты, гипотезы и требования

- **Факт:** E2E вызвал selectOption на кнопке role=combobox и завершился ошибкой, потому что элемент не является HTML select.
- **Гипотеза:** проверка устарела после перехода на custom combobox.
- **Требование:** выбрать типоразмер можно мышью и клавиатурой, а выбранная комплектация обновляется.

Факт подтверждается кодом или артефактом. Гипотезу нужно проверить. Требование должно идти из согласованного поведения продукта.

В аудите тест футера ожидал старую ссылку и подпись. Текущая страница показывает другую структуру. Это доказывает несовпадение теста и интерфейса, но не говорит, какая сторона нарушает продуктовый контракт. Сначала выясните ожидаемую навигацию. Не меняйте приложение только ради зеленого теста.

## 3. Как правильно ставить задачу агенту

Фраза «почини CMS» не задает критерии приемки, границы файлов и сред. Сильная задача включает:

1. Сценарий и наблюдаемый симптом.
2. Ожидаемый результат глазами пользователя.
3. Разрешенные приложения и запрещенные данные/среды.
4. Допустимый тип работы: исследовать, писать тест, исправить, запускать тесты.
5. Проверки и критерии завершения.
6. Формат отчета с фактами, рисками и ограничениями.

~~~text
Исследуй сценарий: [действия] → [фактический результат].
Ожидается: [проверяемое поведение].
Сначала только read-only диагностика через [слои и приложения].
Не меняй [запрещенные репозитории, данные и среды].
Сверь тестовый контракт с реальным поведением; не делай тест зеленым,
изменив ожидания без подтвержденного требования.
В отчете покажи факты, гипотезы, файлы, команды и неизвестные.
~~~

Если разрешены правки, добавьте конкретный scope и обязательные проверки. Не просите агента «сделать правильно» без определения правильного результата.

## 4. Симптом и первопричина

**Симптом** — сайт показывает старый текст после публикации. **Первопричина** — проверенное объяснение потери или рассогласования данных. Возможные причины: draft не вошел в change set, backend не сохранил поле, snapshot отдает прежнюю revision, сборка использовала старый snapshot или браузер не получил обновление.

Не выбирайте первопричину по имени файла. Следуйте за конкретным тестовым значением через каждый слой и определите первое место, где оно отличается от ожидания. Это обычно быстрее, чем менять редактор, API и CSS одновременно.

## 5. Системная отладка

| Шаг | Действие | Пример публикации страницы |
|---|---|---|
| 1 | Уточнить роль, страницу, поле и шаги | Редактор меняет title About |
| 2 | Повторить в безопасной среде | CMS показывает успех, сайт оставляет старый title |
| 3 | Собрать доказательства | Network, request ID, backend log, API/DB read |
| 4 | Найти границу | Сравнить draft, опубликованные данные, snapshot и build |
| 5 | Сформулировать одну проверяемую гипотезу | Snapshot использует прежнюю revision |
| 6 | Проверить гипотезу | Сравнить API и статический revision marker |
| 7 | Добавить тест на найденный контракт | Publish integration и public snapshot assertion |
| 8 | Исправить минимально и проверить соседей | Save/reload, роли, другой тип страницы |

Если дефект нельзя воспроизвести, запишите среду, попытки и недостающие предпосылки. Не заменяйте неизвестность догадкой и не исправляйте код наугад.

## 6. Тестовая пирамида

| Уровень | Проверяет | Пример | Не доказывает |
|---|---|---|---|
| Unit | Одно правило/функцию | publish blockers, сортировка, transitions | Реальную БД и браузер |
| Component/UI | Поведение формы с контролируемыми зависимостями | Валидация CMS editor | Реальную авторизацию и сохранение |
| API/contract | JSON, ошибки и права endpoint | admin operation и capabilities | UI и действия пользователя |
| Integration | Несколько слоев с реальной зависимостью | backend write/read против disposable PostgreSQL | Полный UI/deploy |
| E2E | Пользовательский путь через приложения | login → upload → save → publish → public read | Все роли и все комбинации данных |

Надежный набор содержит много быстрых нижних проверок, интеграционные тесты критических границ и небольшой ряд важных E2E-путей. E2E дороже в поддержке и сложнее в отладке, поэтому не стоит заменять им unit-тесты.

В Bizon прошли 230 CMS unit/UI тестов, но CMS media E2E был заблокирован схемой тестовой БД. Поэтому верно сказать «эти 230 локальных тестов прошли», но нельзя сказать «сохранение в PostgreSQL и публикация доказаны E2E».

## 7. Что такое test harness

**Test harness, тестовая обвязка** — среда, которая готовит зависимости и данные, запускает приложения и тесты, изолирует побочные эффекты и собирает диагностику. Это не только команда запуска.

CMS harness должна иметь:

- disposable PostgreSQL с известной схемой и seed data;
- тестовый аккаунт и роли;
- локальный S3/MinIO и отдельный bucket;
- отдельные порты для CMS, backend и публичной сборки;
- фикстуры и автоматический cleanup;
- блокировку внешних запросов;
- preflight readiness для БД и storage;
- логи, request IDs, Playwright traces и screenshots.

Тест Bizon уже ограничивает DB/S3 loopback-хостами, проверяет E2E в имени БД и bucket, наличие таблиц и блокирует внешние HTTP-запросы. Это хороший safety design. Текущий запуск остановился на readiness схемы. Следующий шаг — документированный bootstrap базовой схемы тестовой базы; нельзя ослаблять проверки и указывать production вместо тестовой БД.

## 8. Фикстуры и моки

**Фикстура** — заранее подготовленный тестовый набор. **Мок** — подмена зависимости контролируемым ответом. Они повышают скорость и повторяемость, но могут скрыть расхождение с реальным сервисом.

Публичный CI build Bizon использует API fixture вместо базы. Это проверяет сборку на форме ответа fixture, но не доказывает, что CMS записала данные. Некоторые упавшие тесты ожидают редакционный текст, которого fixture не содержит. Это возможный дефект покрытия: прежде чем менять приложение, сравните fixture с текущим API-контрактом и утвержденным содержимым.

Правила:

- мокайте нестабильные или дорогие границы, но оставьте integration тест на реальном контракте;
- fixture должна содержать обязательные поля реального API;
- тесты создают собственные записи, а не используют меняющиеся общие данные;
- проверяйте успешный путь и отказ зависимости;
- изолируйте тестовую базу и storage, очищайте данные после падения тоже.

## 9. Регрессионный тест и TDD-цикл

Регрессионный тест закрепляет ранее сломанный сценарий:

1. На исходном коде тест падает ожидаемым способом.
2. Исправление устраняет этот сбой.
3. Тест и соседние проверки проходят.
4. Проверяется пользовательский контракт, а не случайная деталь реализации.

Например, потерю выбранного изображения следует проверять через сохранение asset reference и повторное открытие редактора. Проверка наличия слова save в исходнике этого не доказывает.

Тест custom combobox должен открывать элемент по роли и выбирать доступный option, а не вызывать selectOption на кнопке. Если бизнес-требование требует именно нативный select, тогда корректное решение может быть в интерфейсе. Сначала зафиксируйте контракт, затем меняйте test или product.

## 10. Контракты между слоями и миграции

Контракт — согласованные данные и правила на границе. Для CMS-страницы он может определять ключ, обязательный title, формат медиа, статусы, роли, допустимые переходы, endpoint публикации и структуру snapshot.

Контракт описывает типы, обязательность, ограничения, статусы, ошибки, права, побочные эффекты и совместимость новых полей. В Bizon admin API передает operation name и args; публичный сайт потребляет отдельные published endpoints. TypeScript типов внутри пакетов недостаточно, потому что приложения собираются и развиваются отдельно. Проверяйте реальный JSON и ошибки на границах.

Миграции БД — часть контракта. Безопасная последовательность: добавить совместимое поле/таблицу, развернуть код, заполнить и проверить данные, переключить чтение/запись, наблюдать работу и лишь затем удалять старую схему. Не смешивайте разрушительную миграцию и правку контента без плана восстановления.

## 11. Flaky tests и ложная уверенность

Flaky test при одинаковом коде и данных дает разные результаты. Причины: гонки, общий storage, время, нестабильный selector, анимация, неочищенный localStorage или зависимость от порядка.

В прогоне Bizon некоторые drawer и scroll-проверки падали только в отдельных viewport и местами достигали timeout. Это может быть дефект scroll lock или ошибка локатора. Trace должен показать последний завершенный шаг, DOM, scroll position и network state.

Не лечите нестабильность повтором до PASS. Ретрай может уменьшить шум CI, но скрывает первопричину. Добейтесь изолированных данных, ожидания конкретного состояния и cleanup. Учитывайте частоту падений и сохраняйте артефакты.

## 12. Наблюдаемость

Для связи событий между слоями нужны структурированные логи, request ID, метрики длительности и ошибок, распределенная трассировка, revision сборки и deploy ID.

В Bizon backend пишет request IDs, а публикация использует content revision. При расследовании сопоставьте CMS-операцию, backend request, результат DB read, snapshot revision и публичный build. В отчеты не копируйте cookies, токены, пароли и персональные данные.

## 13. Делегирование агентов

| Ситуация | Поручение | Ожидаемый результат |
|---|---|---|
| Исследование | Проследить сущность по слоям, без правок | Файлы, вызовы, данные, доказательства и неизвестное |
| Debugging | Воспроизвести и проверить гипотезы | Минимальный repro и подтвержденная причина |
| Написание теста | Закрепить согласованный контракт | Тест падает до исправления и проходит после |
| Запуск теста | Проверить заданные команды и среду | PASS/FAIL/BLOCKED, команда, артефакты |
| Исправление | Изменить один подтвержденный слой | Малый diff, целевой тест и регрессия |
| Review | Независимо проверить diff | Конкретные замечания с основанием и приоритетом |

Параллельте независимые вопросы, а не конкурирующие изменения в одном файле. Например: один агент прослеживает CMS API, другой исследует тестовую БД, третий анализирует E2E фикстуры. Назначьте владельца, который сведет выводы. Если несколько агентов одновременно меняют редактор и fixture, возникнут конфликтующие контракты и дублирующая работа.

### Пример задачи на read-only расследование

~~~text
Проследи страницу About от CMS-редактора через admin API и backend
до PostgreSQL, published snapshot, static build и публичного маршрута.
Сценарий: CMS показывает успех публикации, но сайт старый.
Не используй production, не запускай миграции, код не меняй.
Сравни идентификатор и revision на каждом шаге.
Верни таблицу: слой, наблюдение, доказательство, гипотеза, ограничение.
~~~

### Пример задачи на регрессионный тест

~~~text
Причина подтверждена: поле title не попало в published snapshot.
Добавь минимальный regression test, который падает до исправления.
Не меняй E2E ожидания и не расширяй scope на другие типы страниц.
Предложи минимальную правку, затем укажи целевые и соседние тесты.
Не обращайся к production и внешним сервисам.
~~~

## 14. Проверка diff и адаптивной верстки

В корне Bizon есть незакоммиченные изменения и несколько Git-репозиториев. Сравнивайте статус каждого отдельно. Не включайте чужие изменения и generated files в свою правку. Перед сдачей объясните каждый файл в diff.

Для CSS следуйте AGENTS.md: явно задавайте Grid tracks, добавляйте min-width: 0 элементам, которым нужно сжиматься, сочетайте width: 100% с max-width: 100% там, где нужно ограничить размер, используйте mobile-first стили.

В E2E длинный заголовок вышел за track на всех viewport. Проверяйте computed display, grid-template-columns, minWidth, maxWidth, offsetWidth и ширину родителя при конкретном размере viewport. Не скрывайте overflow до определения причины: текст может просто обрезаться.

## 15. Локально, CI, staging и production

1. Локальные unit/type/lint быстро проверяют отдельный код.
2. Integration/E2E проверяют приложения на disposable зависимостях.
3. CI доказывает воспроизводимость на чистом runner.
4. Staging проверяет близкую к production конфигурацию и интеграции.
5. Production smoke проверяет уже выпущенный результат безопасным read-only сценарием.

PASS на одной ступени не подразумевает PASS на следующей. Сборка Bizon на fixture не проверяет живую БД или CMS учетную запись. CMS E2E заблокирован, поэтому публикационный путь не подтвержден.

## 16. Сокращение времени разработки без потери качества

- Воспроизводите дефект коротким сценарием и сохраняйте минимальную fixture.
- Ищите первую границу, где значение расходится с ожиданием.
- Запускайте быстрый тест, способный проверить гипотезу, затем целевую регрессию.
- Стройте harness с автоматическими preflight и cleanup, чтобы не тратить время на ручную подготовку.
- Передавайте агентам результаты и артефакты, а не поручайте повторить весь поиск.
- Записывайте контракт рядом с тестом и API.
- Отделяйте «не запускалось» от «упало» и «прошло».

В Bizon многие unit-проверки проходят, но CMS E2E зависит от схемы тестовой БД. Воспроизводимый bootstrap базы даст больше пользы, чем повторные попытки запускать браузер на неподготовленной среде.

## Сквозной workflow: «после публикации сайт показывает старую страницу»

1. Зафиксировать страницу, поле, роль, URL и ожидаемый текст.
2. Проверить, что используется disposable DB и локальное хранилище.
3. Повторить редактирование, save, reload, submit for publication и дождаться статуса.
4. Записать значения draft, ответа API, DB read, published snapshot, revision и статического HTML.
5. Найти первое расхождение; не менять все слои одновременно.
6. Проверить одну гипотезу минимальным тестом.
7. Добавить regression test на найденный контракт.
8. Исправить ограниченный слой и проверить save/reload, publish, public read и соседнюю сущность.
9. Пройти CI и staging; отдельно удостовериться в production deployment, если это входит в задачу.
10. Передать результат: diff, тесты, среда, revision и оставшиеся риски.

Для параллельной работы агент A может исследовать CMS/API, B — DB и snapshot, C — корректность фикстуры. Сначала read-only результаты, затем владелец задачи выбирает подтвержденную причину. Не запускайте параллельные исправления до этого: они могут лечить разные гипотезы.

## Критерии завершения задачи

- Есть понятные сценарий и критерии приемки.
- Первопричина доказана либо оставшаяся неопределенность названа.
- Тест покрывает дефект или новый контракт.
- Проверки и их результаты точны и воспроизводимы.
- Diff ограничен согласованным scope.
- Миграция и данные имеют безопасную последовательность.
- Логи/артефакты позволяют продолжить расследование.
- В отчете разделены local, CI, staging и production результаты.

Для текущего аудита ближайшие шаги — подготовить изолированную схему E2E-БД и сверить контракт ожиданий для упавших публичных тестов. До этого нельзя утверждать, что CMS проверена end-to-end.
