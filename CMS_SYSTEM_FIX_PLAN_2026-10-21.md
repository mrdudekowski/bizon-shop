# План исправления проблем CMS и медиа

**Дата:** 21 октября 2026 г.<br>
**Статус:** план работ, не реализация.<br>
**Связанный документ:** [варианты системных решений](./CMS_SYSTEM_REPAIR_OPTIONS_2026-10-21.md).<br>
**Область:** frontend-cms, backend-app, публичный сайт, тестовая инфраструктура и затем проверяемая production-доставка.

## Цель и критерий завершения

Привести CMS, backend, хранилище медиа и публичный сайт к согласованному поведению: изображения имеют однозначный адрес и отображаются одинаково во всех потребителях; сервер подтверждает целостность изображения до успешной регистрации; picker доступен в правильной production-сборке; одинаковые числа форматируются одинаково; открытие редактора не выдаёт автоматическую нормализацию за пользовательскую правку.

Работа считается завершённой только после прохождения unit/component/API тестов, изолированного E2E с реальной тестовой БД и S3-совместимым хранилищем, и staging проверки сквозного пути загрузки/выбора/сохранения/публичного отображения. Production deploy и production-запись являются отдельным заключительным этапом, выполняемым лишь после review и согласования конкретного release.

## Принцип проверки тестов: тест не становится зелёным ценой неверного ожидания

Уже обнаружено, что в репозитории есть полезные узкие тесты, но сам факт их прохождения не доказывает, что тест соответствует продуктовой правде. Например, тест локального store может подтверждать поведение mock/local adapter, но ничего не доказывать о PostgreSQL/S3; тест resolver-а с заданным URL не доказывает, что такой же URL приходит из реального API.

Для каждого теста, который добавляется или меняется, вести короткую запись: **требование/контракт → независимый источник истины → сценарий → проверяемый внешний результат → уровень теста**. Источником истины не должен быть тестируемый helper или текущая ошибочная UI-строка. Использовать, в порядке уместности:

1. утверждённое бизнес-правило/контракт API и наблюдаемое поведение требуемого продукта;
2. независимый стандарт/формальная семантика (например, правила склонения), проверенный человеком;
3. реальный fixture, созданный корректной библиотекой/системой либо полученный из безопасной тестовой среды;
4. текущую реализацию — только как объект проверки, никогда как единственное доказательство ожидаемого результата.

**Запрещённый способ “исправить” красный тест:** поменять ожидаемое значение на фактическое без пересмотра контракта; удалить assertion; расширить snapshot; заменить значимый fixture на упрощённый; превратить обязательный вызов в optional; ослабить проверку статус-кода/содержимого; замокать компонент, границу или ошибку, которую данный тест должен проверять.

### Обязательный тестовый review loop

При любом падении:

1. Сохранить точный failing output и минимально воспроизводимый сценарий.
2. Установить, какой слой нарушил требование: код, данные/fixture, конфигурация теста либо само требование.
3. Сверить требование с независимым источником истины и текущим поведением продукта/API. Не переписывать expectation до этого шага.
4. Если падение показывает дефект кода — исправить код и оставить assertion, которое ловит дефект.
5. Менять тест можно лишь при доказанной ошибке самого теста: указать неверное предположение и сослаться на утверждённый контракт; сначала предложить исправленный сценарий и ожидаемое поведение, затем внести минимальную правку.
6. Убедиться, что тест падает на старом/дефектном варианте (regression proof) и проходит на исправленном.
7. Проверить мутацией или контролируемой инверсией ключевой логики, что assertion действительно обнаруживает регрессию. Мутацию вносить только в локальной временной копии/отдельном незакоммиченном diff и полностью удалить до финального прогона.
8. Запустить целевые тесты, затем полный относящийся к изменению набор; записать команды, результат и ограничения.

Тест, который не смог бы упасть при возвращении исходной ошибки, не считается регрессионной защитой.

Начальные ориентиры: `backend-app/src/storage/putMedia.test.ts`, `uploadReadiness.test.ts`, `admin/server/createAsset.test.ts`; `frontend-cms/src/admin/domain/catalogPreviewUrl.test.ts`, `media/PlacementFields.ui.test.tsx`, `MediaLibrary.ui.test.tsx`, `ShopProductList.ui.test.tsx`, `ShopShowcaseEditor.ui.test.tsx`; публичные `src/lib/content/shopCategoryPresentation.test.ts` и тесты опубликованного media snapshot.

6. Проверить, какие image decoder, DB fixtures и object-store emulator уже доступны в зависимостях/CI. Выбрать существующую совместимую возможность, а не добавлять новую библиотеку до оценки.

## Этап 1. Определить контракты и спорные бизнес-правила

До кода зафиксировать короткие решения в ADR/spec (по одному для независимых границ), согласовать acceptance criteria и backward compatibility.

### 1A. Media URL contract

Инвентаризировать все реальные варианты `media.url`: абсолютный S3/CDN URL, `/media/...`, `/api/media/file/...`, путь публичного сайта `/images/...`, пустые/устаревшие/неподдерживаемые значения. Определить, какое поле API несёт исходный asset reference, какое — preview/public URL, и какая сторона отвечает за разрешение site-relative пути. Поле `dataUrl` нельзя считать data URI без проверки: выбрать понятную семантику и описать переход.

Определить поведения для неверного URL: показывать ошибку/placeholder с диагностикой, а не страницу HTML как изображение; не переписывать S3 URL на public-site origin; не конструировать локальный URL при production-конфигурации без origin.

### 1B. Image upload contract

Зафиксировать разрешённые форматы, MIME sniffing/decoding правило, байтовые и размерные ограничения, порядок object-store и DB операций, повторную отправку, поведение при сбое каждого шага, удаление временного объекта, checksum/size metadata. Успех API означает, что файл проверен, объект доступен и metadata соответствует объекту. Не расширять форматы по предположению.

### 1C. Shop tile semantics

Согласовать ожидаемое поведение при создании, переименовании, скрытии/удалении категории и ручном override плитки:

- если список категорий автоматически задаёт состав витрины — tiles производны, обычный GET чистый;
- если редактор должен контролировать snapshot — изменение списка категорий предлагается явным действием с preview, а не неразличимым dirty state при открытии.

Нельзя выбирать поведение тестом или считать текущую реализацию автоматически правильной.

### 1D. Shared count formatting

Проверить правила русского языка для целых неотрицательных количеств и все места использования в обоих приложениях. Выбрать общий package/модуль только если это совместимо с двумя раздельными сборками; иначе документировать один чёткий владелец/способ синхронизации без тяжёлой локализационной платформы.

### 1E. Release identity

Описать, где получить идентичность CMS build (commit SHA/build ID), как связать его с production domain и как проверить, какие assets реально отдаются браузеру. Разделить release backend и release CMS, если это разные Timeweb apps.

**Gate 1:** реализация не начинается, пока спорное поведение tiles и ownership URL не определены. Для production picker сначала можно продолжить read-only release diagnosis.

## Этап 2. Создать безопасную тестовую среду сквозного уровня

### Работы

1. Завести отдельный тестовый профиль CMS/API с проверкой старта: допустимы только явно тестовые host/database/bucket; известные production hosts запрещены allowlist/guard-ом.
2. Использовать disposable PostgreSQL schema/DB и отдельный bucket в локальном S3-compatible emulator либо существующий deterministic adapter. Запрещено наследовать production credentials из пользовательского `.env`.
3. Если используемый emulator/fixture отсутствует, сначала подготовить repeatable local test fixture; не подменять весь persistence layer mock-ами в E2E.
4. Создать тестового admin через fixture/seed только в disposable DB. Не использовать производственные логины и данные.
5. Добавить teardown, который удаляет только ресурсы с однозначным test namespace/prefix, и failure cleanup с сохранением логов/метаданных для диагностики.
6. Автоматически выводить target подключения в логе теста (без секретов); тест останавливается до выполнения сценариев при неправильном target.

### Проверки

- намеренно задать production-like DB host и проверить, что suite прекращается до подключения;
- доказать, что upload object появился только в тестовом bucket и очистка не затрагивает другие ключи;
- запускать suite дважды: результаты и состояние изолированы, тесты не зависят от порядка.

**Gate 2:** пока тестовая изоляция не доказана, никаких интеграционных upload/save тестов и тем более production write не запускать.

## Этап 3. Исправить и проверить media URL contract

### Порядок реализации

1. Ввести/уточнить типизированный контракт media reference и preview/public URL по ADR, сохранив совместимое чтение старых данных.
2. Реализовать единую функцию разрешения согласно контракту и определить её владельца. Не создавать разные, почти одинаковые resolver-ы в компонентах.
3. Инвентаризировать и подключить все CMS consumers: MediaLibrary, MediaPicker, `PlacementFields`, TireModelList inline preview, компоненты через `CatalogRow`, Shop/Material/Page lists, draft diff и другие найденные `img`/`Image` потребители.
4. Проверить backend list/read serialization и публичный consumer. Не менять source URL только потому, что CMS origin не раздаёт публичный asset.
5. Лишь после контрольной выборки решить, нужна ли backfill-миграция. Если нужна: dry-run с количеством и примерами преобразований, backup, идемпотентность, отказ при неоднозначных URL, rollback/restore план.

### Тесты

- **Unit/contract:** публичный относительный путь разрешается ровно на настроенный public origin; абсолютный CDN/S3 URL остаётся неизменным; уже разрешённый URL не получает двойной origin; `/api/media/file/...` обрабатывается согласно действующему контракту; пустое/неподдерживаемое значение даёт ожидаемый fallback/error.
- **API contract:** `listAssets` сериализует URL с согласованной семантикой; тест использует реальные DB row формы и проверяет JSON boundary, не только mapper/helper.
- **UI component:** одна запись показывается одинаково в библиотеке, picker, placement preview, inline/list/diff; тесты утверждают фактический `src` или понятное состояние ошибки.
- **Negative/regression:** вернуть поведение прямой подстановки `/images/...` относительно CMS origin и убедиться, что assertion падает; подать HTML URL и убедиться, что UI не считает его валидным изображением.
- **Public rendering:** опубликованный snapshot с legacy URL и S3 URL отображает правильные адреса; убедиться, что CMS fix не регрессировал public site.

### Test-integrity review

Проверить, что список expected URLs взят из спецификации и адресов сред, а не скопирован из кода resolver-а; fixture публичных premium изображений сверить с реальными путями/содержимым. Не полагаться лишь на `toHaveAttribute('src', ...)`: для boundary smoke проверить, что ответ адреса имеет image MIME и декодируемые байты.

**Gate 3:** никакой массовой замены URL до успешной проверки всех типов и двух клиентов (CMS/public) на legacy fixtures.

## Этап 4. Защитить целостность загрузки изображения

### Порядок реализации

1. Проследить `createAsset`/`replaceAsset` до `uploadAndPersistMedia` и определить точки отказа object store и БД.
2. Выполнять проверку реального декодирования в пределах лимитов, безопасно ограничивать ресурсы декодера, сопоставлять detected format с разрешённым типом; не верить только имени/Content-Type/8-byte signature.
3. Согласовать checksum и size metadata с фактическим объектом. Не делать отдельную запись usable asset до подтверждённого object-store результата.
4. При DB failure после успешной загрузки применять текущий согласованный compensation/cleanup path; если cleanup не подтверждён — оставить диагностируемое состояние/cleanup-required, не отвечать ложным успехом.
5. Зафиксировать retry/idempotency: повтор того же запроса не должен незаметно плодить дубликаты или ссылаться на неверный объект.
6. Исследовать существующий 16-byte объект read-only. Замена/удаление — отдельная управляемая операция после сверки использования и записи.

### Матрица обязательных тестов

| Сценарий | Ожидаемый внешний результат | Состояние БД/S3 после результата |
|---|---|---|
| Полное валидное PNG/JPEG из проверенного fixture | Успех с ожидаемым ID/MIME | В БД одна запись; объект читается и совпадает по size/checksum |
| Файл обрезан после корректной сигнатуры (в том числе fixture, аналогичный 16-byte объекту) | Явная validation error, не 500/успех | Нет usable metadata; временный объект отсутствует или cleanup явно подтверждён |
| Содержимое не PNG, но имя/MIME объявлены PNG | Validation error | Нет usable записи/объекта |
| Повреждённый JPEG/неполный файл, пустой файл | Validation error | Нет usable записи |
| Валидный файл неподдерживаемого типа | Отказ согласно контракту | Нет объекта и записи |
| Размер выше лимита | Отказ до дорогой обработки | Нет объекта и записи |
| Object store write/read/metadata failure | Ошибка без ложного успеха | DB не содержит активный asset; cleanup state проверяем |
| DB persist failure после успешного put | Контролируемая ошибка/cleanup result | Объект компенсирован либо явно отмечен для cleanup; нет сирот без наблюдаемости |
| Replace existing asset | Успех только после нового объекта/metadata | Ссылка старого asset сохраняется до атомарного подтверждения replacement |

Fixture должен быть настоящим минимальным изображением, созданным/проверенным независимым decoder-ом; malformed fixtures формируются контролируемым усечением валидного файла. Не применять микрофайлы, которые текущий mock объявляет PNG без проверки настоящего содержимого.

### Test-integrity review

- Проверить старые тесты `putMedia.test.ts` и `uploadReadiness.test.ts`: какие фиктивные PNG байты используются и что текущие ожидания считают валидным; если fixture не декодируется, это признак проблемы в тесте/валидации — выяснить контракт, не просто заменить expected status.
- Проверить, что тест действительно проваливается при удалении decode validation или при принятии 8-byte signature-only файла.
- Проверить баланс ресурсов и cleanup в fake store, а минимум один API интеграционный сценарий — в disposable object store + PostgreSQL.
- Нельзя объявлять DB/S3 целостность доказанной тестом, который mock-ает и DB, и storage.

**Gate 4:** неполный файл должен быть отвергнут API и не появляться в библиотеке после повторного list; валидный — пройти S3 GET и DB reload.

## Этап 5. Восстановить доказуемую production CMS сборку и галерею

### Сначала read-only diagnosis

1. Связать production CMS hostname с конкретным Timeweb app/статическим сайтом.
2. Записать repository, branch/ref, build command, output directory, нужные public environment variables и deployed commit/build ID.
3. Сопоставить commit с веткой, содержащей `MediaPicker` и UI tests. Проверить, реально ли ожидаемый компонент присутствует в отдаваемом JS/DOM.
4. Проверить cache headers/asset fingerprints и различить старый deployment от stale browser/CDN cache.
5. Проверить feature flags/roles лишь при наличии конкретного runtime gate в реальном артефакте/config.

### После определения причины

- неправильный source/branch — исправить deployment mapping и закрепить его автоматической проверкой;
- отсутствующий release — выпустить правильный CMS artifact после staging проверки;
- stale cache — исправить cache/version strategy, затем проверить чистую сессию и hard reload;
- правильный build, но неверное поведение — локализовать конкретный runtime config/permission defect и добавить тест на него.

### Тесты и acceptance

- **Build test:** production build содержит нужную версию/идентичность и gallery component.
- **UI tests:** в hero, shop tile и carousel поле есть корректный gallery action; недоступные/неиспользуемые медиа фильтруются по утверждённому правилу; загрузка остаётся работоспособной; cancel не меняет поле.
- **Flow test:** выбрать asset → сохранить draft/change set → перечитать из API → reload страницы → preview остался выбранным; затем проверить публичный preview только в staging.
- **Deployment smoke:** получить asset с deployed origin, проверить build id, JS response и DOM после новой browser context.
- **Regression:** CI должна остановить release, если deployment manifest/build SHA не соответствует ожидаемому commit.

Не считать тест source-level наличия `<MediaPicker>` доказательством production доставки.

**Gate 5:** production deploy допускается только если staging build из проверенного SHA показывает picker и сквозное сохранение работает. Текущий план не выполняет деплой.

## Этап 6. Выравнять plural formatting CMS и сайта

### Работы и тесты

1. Просмотреть все места подписи количества, включая обе найденные строки Shop и остальные найденные CMS/public surfaces.
2. Вынести только чистую функцию форматирования с ясной входной областью и согласовать способ потребления двумя независимыми приложениями.
3. Написать тесты по утверждённым языковым правилам для `0, 1, 2, 4, 5, 11, 12, 14, 21, 22, 25, 101, 111`; проверить отрицательное/дробное/NaN поведение, если такие значения допустимы на уровне UI.
4. Проверить CMS product list и category editor на фактические подписи; сравнить с публичным сайтом на одинаковых counts.

### Защита от теста, подстроенного под дефект

Expected outputs сверить с формальным правилом русского plural и независимым ручным разбором, не копировать текущие публичные строки как единственный oracle. Мутационно изменить ветвление для `1` и `11` и убедиться, что тесты падают; удалить дублированный фиксированный суффикс только после проверки всех мест.

**Gate 6:** единый модуль не вводится, если он создаёт неподдерживаемую зависимость/сборочную связь; тогда выбрать минимальный договорённый модульный подход и покрыть parity тестами.

## Этап 7. Разрешить и исправить Shop initial dirty state

Этот этап условный: не выполнять, пока product rule не выбрано.

### Если tiles производны от списка категорий

- Сделать нормализацию derived read model, не пользовательской правкой.
- Сравнивать пользовательские overrides, а не результат автоматического merge.
- Тесты: load не dirty; GET не вызывает write; новая категория появляется по правилу; existing order/image/title overrides сохраняются; скрытая/удалённая категория ведёт себя согласно спецификации; после сохранения и reload результат стабилен.

### Если tiles — редакторский snapshot

- Не включать новые категории молча в dirty draft.
- Представить отдельное предложение синхронизации состава с preview и явным действием редактора.
- Тесты: обычное открытие чистое; предложение само не пишет; отмена сохраняет состояние; подтверждение создаёт ожидаемый draft; существующие настройки не теряются; re-open/reload соответствует snapshot.

### Доказательство отсутствия скрытой записи

Для обоих вариантов API mock/spy тест полезен только как быстрый component guard. Обязательный integration test сравнивает DB revision/updated_at/content до и после открытия в disposable DB. Для regression proof отдельно проверить, что исходный алгоритм merge не может вновь выставить dirty при неизменённом состоянии.

## Этап 8. Полный локальный E2E journey

Собрать тестовый admin workflow на disposable services. Не использовать production сессию.

1. Login тестового пользователя, истёкшая/неверная сессия, logout.
2. Открыть медиа библиотеку и проверить известный asset URL/preview.
3. Загрузить валидный файл; проверить success UI, API record, PostgreSQL metadata и GET из object store.
4. Попытаться загрузить повреждённый файл; проверить объяснимую ошибку и отсутствие usable записи.
5. В редакторе использовать галерею: отфильтровать доступное медиа, выбрать существующий asset, отменить другой выбор.
6. Сохранить draft/change set; обновить страницу и повторно прочитать API/DB.
7. Опубликовать только в disposable environment, если этот путь поддержан fixture; проверить опубликованный payload.
8. Отобразить опубликованное изображение в публичном приложении на тестовом origin и проверить bytes/MIME, не только наличие тега.
9. Проверить один и тот же результат после полного reload и новой browser context.
10. Проверить denied/expired token и ошибки API/storage; пользователь не должен видеть ложное состояние успеха.

### Требования к надёжности E2E

- Тесты используют уникальные фиксированные test IDs/namespaces и очищают только свои данные.
- Нет зависимости между тестами по порядку; каждый может повторяться.
- Flaky retry не превращает нестабильный сценарий в pass: фиксируются исходная ошибка и повтор.
- Артефакты отказа сохраняют screenshot, console/network diagnostics и correlation ID без секретов.
- E2E подтверждает persistence повторным чтением из другого запроса/контекста, не UI toast или optimistic state.

## Этап 9. Staging verification и release decision

1. Развернуть каждое приложение из зафиксированного SHA в staging; CMS/backend версии и public origin записать в release manifest.
2. Выполнить тесты этапов 3–8 на staging с отдельными DB/S3 и test accounts.
3. Проверить логи backend: upload response, validation rejection, storage operation, persistence outcome. Сверить correlation IDs и размеры/checksum.
4. Снять production-like UI состояние для picker, MediaLibrary, Shop editor и public category; проверить отсутствие horizontal overflow на целевых ширинах, если меняется соответствующая вёрстка.
5. Выполнить ручной release review: changed files, миграции, env, rollback, media data impact, build SHA, test integrity table.
6. Production deployment выполнять как отдельный согласованный шаг. После deploy — read-only smoke: hostname/build ID, открытие галереи, чтение выбранного media, публичное отображение. Не загружать/удалять произвольные production объекты без утверждённого тестового протокола.

## Набор проверок по уровням

| Уровень | Что должен доказать | Чего не доказывает сам по себе |
|---|---|---|
| Unit | чистые правила URL/validation/count/tile normalization | сериализацию API, S3, реальный DOM/deploy |
| Component/UI | кнопки/ошибки/preview и пользовательские переходы | реальное сохранение в БД/S3 |
| API contract | request/response и validation boundary | deployed CMS artifact и браузерный кэш |
| Integration | PostgreSQL + object storage ordering/cleanup/reload | production configuration/runtime |
| E2E local | полный journey на disposable stack | production domain и release chain |
| Staging smoke | candidate artifacts, интеграция и UI на реальной конфигурации | корректность production данных без read-only сверки |
| Production smoke | deployed SHA, доступность picker и чтение существующих media | upload/persistence, если запись намеренно не выполнялась |

## План контроля тестовых правок

Каждый PR/пакет должен содержать таблицу:

| Изменённый тест | Почему прежний вариант недостаточен/ошибочен | Требование и независимый oracle | Как тест падает на старом дефекте | Проверка мутацией | Команды/результат |
|---|---|---|---|---|---|
| Заполняется автором этапа | Не менять тест лишь для зелёного прогона | Ссылка на ADR/стандарт/контракт/fixture provenance | Конкретный регрессионный сценарий | Конкретная инверсия/удаление защиты | Точные команды и ограничения |

Reviewer проверяет production code diff и test diff раздельно. Любое изменение ожиданий требует объяснения; если меняется продуктовый контракт, сначала меняется/утверждается контракт и только затем expectation. Для snapshot updates показать смысловой diff, не использовать `--update` как механическое лечение.

## Порядок поставки и зависимости

1. Этап 0 — аудит текущего состояния и тестов.
2. Этап 1 — контракты, спорные решения; этап 5 diagnosis может идти параллельно только в read-only режиме.
3. Этап 2 — защищённая тестовая инфраструктура.
4. Этапы 3 и 4 — независимые изменения media URL и image integrity; каждый со своим backend/CMS scope и regression suite.
5. Этап 5 — сборка/release picker после определения истинного target; может выпускаться независимо от data migration.
6. Этапы 6 и 7 — небольшие отдельные UX/logic изменения; этап 7 только после продуктового выбора.
7. Этапы 8–9 — общая интеграция и staging/release gates.

Не объединять в одну миграцию S3/DB очистку, URL нормализацию, редакторское поведение и deploy. Все data migrations должны быть отдельными, идемпотентными, с dry-run и обратимым планом.

## Артефакты каждого этапа

- **0:** baseline + test inventory + deployment map.
- **1:** ADR/контракты и acceptance criteria.
- **2:** тестовый профиль, isolation guard и проверка target безопасности.
- **3:** URL contract tests, consumer inventory, при необходимости отдельный dry-run миграции.
- **4:** upload lifecycle, matrix tests, валидные и повреждённые fixtures, S3/DB reconciliation.
- **5:** доказанный production target/build identity и release checklist для gallery.
- **6:** общий/согласованный formatter и parity tests.
- **7:** утверждённый tile semantics и тесты чистого открытия/явной синхронизации.
- **8:** повторяемый E2E отчет со сквозными IDs и подтверждённым reload.
- **9:** staging evidence, diff/test review, rollback и отдельное release решение.

## Условия остановки

Работы останавливаются до выяснения, если тест может подключиться к production; source of truth для URL/tiles не согласован; фикстура не соответствует заявленному типу; assertion нельзя объяснить независимо от реализации; миграция не имеет dry-run/rollback; build ID production не определён; upload вернул успех при невозможности прочитать объект или подтвердить metadata. В отчёте фиксируются факт, риск и минимальный следующий шаг — не ослабляется проверка ради продолжения.

## Изменения, которых этот план не разрешает автоматически

Планирование не является разрешением на production deploy, миграцию/удаление DB или S3 данных, замену повреждённого объекта, изменение auth TTL либо массовое преобразование URL. Эти действия требуют подготовленного конкретного diff/runbook и отдельного review до применения.
