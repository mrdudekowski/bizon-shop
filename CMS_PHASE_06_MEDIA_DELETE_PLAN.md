# Фаза 6 — универсальная отвязка медиа при удалении

Дата: 2026-10-08  
Статус: **реализация завершена; DB/S3 integration proof ожидает снятия blocker фазы 5C**.

Связанные документы: [общий аудит](./CMS_TEST_COVERAGE_AUDIT_2026-10-08.md), [план DB integration](./CMS_PHASE_05C_DATABASE_TESTS_PLAN.md).

## Требование

- На карточке файла с использованиями показывать зелёный светящийся индикатор.
- Перед удалением предупреждать, где файл используется; пользователь подтверждает отвязку и удаление.
- Удалять ссылки универсально: published relational columns, gallery relations, drafts и change sets.
- Сохранить удаление объекта хранилища после commit и историю удаления.

## Реализация

- `frontend-cms/src/admin/media/MediaLibrary.tsx`: карточка показывает индикатор; действие доступно для используемого файла; confirm перечисляет все известные места и поясняет, что ссылки будут очищены.
- `frontend-cms/src/admin/client/localStore.ts`: рекурсивно очищает media ID в сохранённом состоянии перед удалением файла.
- `backend-app/src/storage/mediaReferences.ts`: чистая рекурсивная обработка JSON и SQL helper для прямых колонок, relation tables, `cms_drafts`, `cms_change_sets`.
- `backend-app/src/admin/server/postgresAdmin.ts`: разрешает delete после проверки разрешений/хранилища, удаляет target под row lock и запускает ссылочную очистку в serializable transaction. Если есть ожидающая замена, она тоже отменяется, её ссылки очищаются, staged object удаляется после commit. История и обе cleanup queue записи сохраняются атомарно.
- `listAssets` сообщает также ссылки из Shop catalog tiles и Tire IQ articles.

## Ограничения и дальнейший порядок

Настоящий PostgreSQL/S3 контур и runtime rollback не проверены. Перед выдачей статуса production-ready выполнить фазу 5C на утверждённой schema-only baseline и одноразовом PostgreSQL, проверить все UPDATE/DELETE в транзакции, ошибки SQL, rollback, историю/cleanup queue и удаление object после commit. Корневой dev Compose volume `bizon_pg_data` использовать нельзя.

## Дополнительный дефект загрузки изображений из CMS

**Источник:** скриншот от пользователя от 2026-10-08, редактор категорий Shop, поле «Фото для карусели». Для двух категорий CMS показывает: «Хранилище файлов сейчас недоступно. Файл не загружен. Попробуйте позже.»

**Статус:** зарегистрировано для расследования; причина пока не установлена. Это отдельный сценарий от отвязки и удаления существующих файлов.

### План расследования

1. На staging воспроизвести загрузку одним новым временным изображением в безопасное QA-поле; не перезаписывать текущие материалы.
2. Сопоставить ответ UI с запросом `/v1/admin/media` и backend-ошибкой; установить, отклонён ли запрос до обращения к S3 или самим хранилищем.
3. Без раскрытия секретов проверить наличие и корректность имён S3-переменных (`S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_REGION`, `S3_ENDPOINT`, `S3_PUBLIC_URL`, `S3_FORCE_PATH_STYLE`), доступность endpoint, bucket и требуемые права записи.
4. Проверить ограничения размера/MIME, формат multipart или тела загрузки, timeout и обработку сетевых ошибок; выяснить, не скрывает ли интерфейс разные причины одним общим сообщением.
5. После исправления повторить загрузку QA-файла, перечитать список файлов, проверить отображение превью и доступность публичного URL. Затем удалить только созданный QA-файл и подтвердить очистку metadata/object.

### Критерии завершения

- Загрузка через CMS завершается успешно; файл сохраняется после обновления страницы и открывается по ожидаемому URL.
- Ошибки конфигурации, авторизации, сети, размера и формата дают различимые безопасные сообщения.
- QA-артефакт удалён после проверки.

### Гипотеза причины ошибки — ожидает runtime-проверки

- Backend `backrooms` (`266233`) требует `S3_BUCKET`, `S3_ACCESS_KEY_ID` и `S3_SECRET_ACCESS_KEY` в `backend-app/src/storage/env.ts`; также требует `S3_PUBLIC_URL`. При отсутствующей обязательной S3-конфигурации `assertMediaUploadReady` выбрасывает `storage_unavailable`, а CMS отображает именно текст со скриншота через `uploadErrorText`.
- На первом осмотре панели была видна переменная `S3_ACCESS_KEY_ID`, но скриншот пользователя содержал только обрезанное имя `S3_ACCESS_KEY_…`. По нему нельзя было установить, есть ли отдельный `S3_SECRET_ACCESS_KEY`. Предыдущее утверждение об отсутствии секрета и подтверждённой причине было ошибочным.
- Пользователь подтвердил, что добавил нужную переменную. Повторная проверка панели Timeweb для `266233` сейчас показывает `S3_SECRET_ACCESS_KEY` в списке; значение не открывалось и не читалось.
- После добавления переменной приложение `266233` показывало статус «В сети несколько секунд»; runtime-логи подтвердили новый старт PM2 и `backend-app listening on 0.0.0.0:4000` в 03:11:32. Кодовая версия остаётся `6b8c3d9`, нового коммита для применения переменной не требовалось.
- Отсутствие `S3_SECRET_ACCESS_KEY` было лишь гипотезой. Если после перезапуска ошибка останется, следующие возможные причины — неверное/неподхваченное значение, права ключа на `HeadBucket`/запись, настройки bucket/endpoint/region или сетевой отказ. Текущий `storage_unavailable` маскирует эти причины одним сообщением.

### Восстановление и проверка

1. Пользователь добавил `S3_SECRET_ACCESS_KEY`; Timeweb теперь показывает её имя, а runtime-логи подтверждают перезапуск backend `266233` и успешный старт.
2. Загрузка через CMS не проверена: безопасный file chooser запретил передачу тестового файла на `mrdudekowski-bizon-shop-e454.twc1.net/shop/`. Не обходить отказ другим способом.
3. Для завершения runtime-проверки пользователь может разрешить загрузку в браузере или сам загрузить QA-изображение через раздел Shop → Оформление Shop. После этого сверить результат в UI/библиотеке файлов и runtime-логах, не раскрывая секрет.
4. Если `storage_unavailable` повторится, определить, отказывает ли конфигурационная проверка или `HeadBucket`; текущий код сводит обе причины к одному ответу.

### Диагностика: в публичной карусели Shop только две категории

- Проверен публичный `/shop` на `mrdudekowski-bizon-shop-931a.twc1.net`: в режиме карусели доступны «Кемпинг и путешествия» и «Прицепы»; оба слайда и их изображения открываются. Переключатель карточек показывает все пять категорий.
- В CMS `/shop` → «Оформление Shop» сейчас пять строк карусели; четыре имеют фото и включённый флажок показа, у «Масла и запчасти» фото нет. При этом форма сообщает «Есть несохранённые правки», а «Опубликовать» отключено.
- Причина расхождения — разные состояния данных: редактор Shop объединяет в локальном `draft` плитки из категорий и их carousel-фото (`ShopShowcaseEditor.mergeCategories`), а сайт читает только опубликованные `shop-home.catalog.tiles` (`readShopHomePatch`). В редакторе видимые фото поэтому ещё не доказывают, что эти плитки записаны и опубликованы в `shop-home`. Публичный рендер фильтрует карусель по наличию опубликованного `carouselImageUrl` (`shopHomeCarouselSlides`).
- Это не общий дефект показа картинок: текущие два опубликованных слайда визуально отображаются. Для вывода остальных четырёх фото на сайт необходимо сначала сохранить конфигурацию Shop, затем опубликовать страницу и дождаться соответствующего frontend-деплоя. Во время read-only проверки ничего не сохранялось и не публиковалось.
