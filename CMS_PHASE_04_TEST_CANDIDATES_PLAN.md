# Фаза 4 — решение по кандидатам на переписывание тестов

Связанные документы: [аудит покрытия](./CMS_TEST_COVERAGE_AUDIT_2026-10-08.md), [журнал требований](./CMS_PHASE_02_DECISION_LOG.md), [архитектура тестов](./CMS_PHASE_03_TEST_ARCHITECTURE_DESIGN.md). Статус: **план; тесты и файлы не менялись**.

## Цель

Разобрать только тесты, для которых аудит обнаружил слабые проверки, source-text assertions, неясную исполняемость или возможное дублирование. Для каждого файла принять проверяемое решение: оставить, заменить поведенческим тестом, дополнить позже integration тестом или признать неисполняемым. Ничего не удалять по сходству названий.

## Кандидаты и предлагаемый исход

| Файл/набор | Наблюдаемое ограничение | Предлагаемое действие на фазе |
|---|---|---|
| `frontend-cms/src/admin/client/remoteRequest.test.ts` | читает текст `localStore.ts`; не вызывает реальный client/request | Переписать на публично тестируемое поведение: cookie credentials, method/body, HTTP/network error mapping, сохранение baseline для conflict |
| `frontend-cms/src/admin/pages/PageEditor.contract.test.ts` | нарезает JSX по именам функций; не подтверждает ожидаемое размещение полей на двух экранах | Переписать на проверку данных/DOM: Page editor не владеет Shop carousel; Shop showcase показывает и сохраняет её |
| `frontend-cms/src/admin/pages/pageListPreview.test.ts` | зависит от точных строк вызова `listAssets` и JSX атрибута | Поведенчески проверить, что preview выбирает URL для связанного media ID и пустое состояние без media |
| `frontend-cms/src/admin/shop/ShopShowcaseEditor.contract.test.ts` | проверяет строки интерфейса/имена вызовов в исходниках нескольких файлов | Переписать на действия пользователя и сохранённый payload; оставить уникальную бизнес-границу, если она подтверждена |
| `frontend-cms/src/admin/media/PlacementFields.upload.test.ts` | проверяет присутствие/отсутствие строк в компоненте | Переписать на upload/replace client calls и отображённый результат/ошибку; не проверять внутреннюю реализацию чтения файла |
| `frontend-cms/src/admin/ui/documentActionCopy.test.ts` | source scan для aria feedback и error copy | Оставить временно как охранную проверку доступных сообщений; после создания browser harness перенести на роль/статус сообщения в DOM |
| `src/components/shop/forgedView.test.mjs` | Vitest include `src/**/*.test.ts` его не выбирает; CI не вызывает `node --test` отдельно | Сохранить чистые domain cases и решить исполняемость: включить совместимым способом либо отдельный явно запускаемый скрипт; удаление не рассматривать без доказательства устаревания |
| `backend-app/src/migrations/*History.test.ts`, `media*Migration.test.ts`, `shopCatalogShowcase.test.ts` | проверяют наличие SQL фрагментов/регистрацию, не применимость к PostgreSQL | Оставить быстрыми migration-intent checks; дополнить применением к disposable DB после schema baseline, не объединять/удалять сейчас |
| CMS/backend пары `changeSetTransitions`, `draftDiff`, `changeSetGrouping`, `editorPermissions` | похожие правила реализованы в двух пакетах | Оставить раздельно, пока пакеты имеют отдельные реализации; добавить parity contract, если нужно гарантировать общий контракт; не удалять дубли автоматически |

## Последовательность

1. Для каждого файла определить владеемый им контракт и связать с утверждёнными R2-01…R2-05 правилами.
2. Проверить, есть ли реализация контракта и stable public seam для поведенческой проверки; если seam отсутствует, предложить минимальный тест seam отдельно, не менять код.
3. Составить карту `текущий тест → ловимая регрессия → предложенная замена → доказательство эквивалентной/лучшей защиты`.
4. Разделить простые unit replacement, CMS DOM/browser replacements, DB migration tests и CI discovery issue. Не делать вид, что всё заменит один уровень.
5. После согласования этой карты попросить отдельное разрешение на выполнение тестов (исходная миссия запрещает запуск без него), затем переписывать по одному набору, сохраняя старый test до готовности замены.
6. Удалить старый тест только после проверки, что новый реально исполняется в CI, накрывает тот же или более сильный контракт, и пользователь согласовал конкретный список файлов.

## Входы

- Утверждённые продуктовые правила R2-01…R2-05.
- Фаза 3 design: тестовые уровни и разделение CMS UI/DB/public site.
- Неизменённая исходная рабочая копия; до чтения каждого кандидата проверить его текущее содержимое, так как checkout содержит незакоммиченные изменения.

## Завершение фазы

Для каждого кандидата имеется обоснованное решение и проверяемая цель замены. В этой фазе не меняются и не запускаются тесты. После утверждения плана работа по реализации замен будет отдельной фазой, со своим объёмом, разрешением на выполнение тестов и отчетом по пакетам.
