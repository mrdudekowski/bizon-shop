## Дополнительная статическая сверка (2026-10-08)

- **Редактирование и отправка на review — отдельные действия.** `saveTireDirection` проверяет `edit_catalog`, пишет overlay, вызывает `rememberMutation` и возвращает запись; `submitChangeSet` отдельной командой переводит change set в `pending_review`. Поэтому наличие очереди само по себе не доказывает, что каждый editor save автоматически требует review.
- **Backend capability gate.** `createPostgresAdminClient` использует общую `requirePermission` → `canEditorPerform`. По текущему helper editor имеет `edit_catalog`, и может получить `create_catalog_items` или `edit_site_pages` по capability; `publish`, `hide`, `delete`, `manage_users`, `review_queue` для editor сейчас отклоняются.
- **Опубликованная запись защищена от некоторых удалений.** Delete для ряда сущностей блокируется, если запись published; удаление родителя также блокируется при наличии детей. Hide обычно переводит запись в `archived`; unpublish для каталога переводит статус обратно в `draft`. Исключения/условия разные по типам, их надо утвердить и покрыть отдельно.
- **Медиа удаляется по схеме deferred cleanup.** Backend проверяет published references, CMS draft/change-set references и ожидающую замену; удаляет DB row и ставит `cms_media_cleanup`, затем после commit удаляет объект в storage и снимает cleanup marker. При ошибке cleanup marker сохраняется для повторной обработки. Это кодовая стратегия, а не runtime-доказательство восстановления.
- **Конкурентность сейчас оптимистичная.** Save требует ранее загруженный `savedDraft`; отсутствие baseline или несовпадение JSON приводит к `conflict`. Из кода не следует, что ввод второго редактора автоматически сливается или сохраняется после конфликта.

Эти пункты добавляют проверяемые факты к R2-01…R2-05, но не заменяют продуктовые решения. Тесты и реальные сервисы по-прежнему не запускались.

### Сопоставление R2-01 с текущим кодом

В backend `rememberMutation` вызывает `recordEditorMutation`; для роли editor функция собирает изменения в открытый change set. `DocumentReviewFooter.tsx` показывает редактору, что draft не попадёт на сайт до одобрения, и предоставляет submit. `submitChangeSet` переводит пакет в `pending_review`; `publishChangeSet` требует `review_queue`, атомарно публикует entries и меняет статус пакета. Это статические признаки того, что основной путь соответствует утверждённому правилу. Реальный API/DB/UI проход ещё не выполнен. Публикация администратором напрямую тоже присутствует в отдельных editor operations; проверить, что этот путь фактически является admin-approved действием и не позволяет обойти review для изменений, внесённых editor.

### Сопоставление R2-04 с текущим кодом

В текущем checkout уже присутствует кодовый путь: backend фиксирует ожидаемую content revision, получает deploy ID, предоставляет status lookup; build wrapper формирует marker; `AdminShell.tsx` помечает сайт обновлённым после статуса deployment success и `contentStatus === "matches"`. Это исходниковое свидетельство, не runtime-доказательство. Остаются проверки build/deploy фактической среды, совпадение digest при реальном контенте, сетевые отказы/повторный polling и сохранение ожидания после reload.

### Сопоставление R2-05 с текущим кодом

Сейчас `listAssets` возвращает `usedBy` для опубликованных связей, CMS drafts и change sets, а `MediaLibrary.tsx` перечисляет места использования. При использовании удаление в UI выключено, а `deleteAsset` в backend возвращает `media_in_use`. Зелёного кружка в карточке не обнаружено. Это расходится с утверждённым правилом «удалить и отвязать везде»; отметить как изменение требований и критический риск целостности данных. Будущий тест должен проверять все таблицы/поле-ссылки, drafts/change sets, пустые optional поля/галереи и отсутствие ссылок после удаления. Невалидные по бизнес-правилам сущности после отвязки должны оставаться draft/hidden либо блокировать публикацию валидатором, но не должны незаметно публиковаться без изображения.
