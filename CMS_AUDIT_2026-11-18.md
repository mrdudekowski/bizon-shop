# Аудит CMS Bizon и результаты проверок

Дата проверки: 18 ноября 2026 года
Область: публичный сайт, frontend-cms, backend-app и доступные локальные тестовые контуры. Проверка кода и запуск тестов — локально; staging и production не изменялись.

## Резюме

CMS состоит из нескольких связанных, но отдельно собираемых приложений. Административные сценарии работают через backend API и PostgreSQL; медиа дополнительно сохраняются в S3-совместимом хранилище. Публичный сайт получает опубликованный контент через API, использует его при статической сборке и обновляет часть данных после загрузки страницы. Публикация и обновление публичной версии поэтому являются отдельными стадиями.

## Границы и состояние рабочей копии

В корне находятся три приложения: публичный Next.js сайт, CMS Next.js и backend API. Последние два имеют собственные Git-репозитории. Проверка не обращалась к production и не выполняла миграций или изменений содержимого.

До начала тестов были обнаружены незакоммиченные изменения:

- в корневом репозитории: CSS каталога и формы, JSX runtime, а также неотслеживаемые skills-lock.json и tmp/;
- в CMS и backend: неотслеживаемые .superpowers/ и tmp/.

Эти изменения не редактировались и не удалялись. После тестов Git показывает тот же перечень. Сборка и Playwright создавали только игнорируемые/generated артефакты. Root E2E был прерван после завершения всех 256 сценариев, поскольку процесс завис на финализации и не вывел штатную сводку; число прошедших и пропущенных сверено по тестовым результатам, ошибочным артефактам и условиям skip в конфигурации. Ошибочные контексты и трассы остались в test-results/.

### Повторная проверка и первичная классификация

После утверждения плана базовые Vitest-команды CMS, backend и публичного сайта были запущены повторно. Результаты совпали с исходным аудитом: CMS и backend прошли, публичный сайт сохранил те же 8 падений в 5 файлах. Отдельно повторно выполнены lint и typecheck публичного сайта: lint завершился без ошибок и с 16 предупреждениями; typecheck завершился с двумя ошибками в `CartPage.test.tsx` и `ContactRequest.test.tsx`, где React `createElement`-вызовы передают `children` третьим аргументом, но типы требуют его также в объекте props.

Три группы runtime unit-падений (`MainHero`, `BrandingCampaign`, `HomeSections`) используют текстовые обходчики, которые читают только `props.children`. Корневой `jsxImportSource` указывает на `src/lib/bizon-jsx`, где видимые строки превращаются в элементы `BizonText` с полем `props.value`. Поэтому текущие обходчики не наблюдают текст, который передается JSX-оберткой. Это сильное подтверждение дефекта тестового наблюдателя; следующий шаг — проверить поведение через DOM/static render и исправить тестовый helper, не менять публичные компоненты на основании этих ошибок.

В `SiteFooter.test.ts` проверяется сырой HTML-substring для подписи с `BIZON`, которая получает вложенную разметку; проверку нужно перевести на видимый/доступный текст, сохранив подтверждение href. В `styleTokens.test.ts` правило считает `letter-spacing: inherit` нарушением, хотя значение наследуется и не задает отдельный tracking; согласовать статическое правило с design-token контрактом до изменения CSS.

На этапе первичной проверки `docker ps` не смог подключиться к Docker Desktop Linux engine. Этот блокер позже снят после подтверждения пользователя; локальный DB/S3 прогон отражен в дополнительном результате ниже.

Для публичного сайта дополнительно создан чистый изолированный worktree на том же `HEAD`, там повторены baseline и Playwright. Полный E2E запуск завершился штатно за 10,3 минуты: 128 passed, 32 failed, 96 skipped. Это 20 уникальных сценариев с падением; повторения по viewport не считаются независимыми дефектами. 96 пропусков обусловлены отсутствием API-тестового окружения и условиями, ограничивающими mobile/desktop-only тесты одним проектом.

В изолированном worktree исправлены все 8 unit assertion failures как тестовые наблюдатели/ожидания, добавлена реакция wheel-catalog на сброс фильтров, обновлены E2E-тесты размера шины и футеров к текущему DOM, подписи и canonical routes. Полная root Vitest регрессия после исправлений: 471/471 PASS; typecheck PASS; lint PASS с 16 предупреждениями. Четыре целевых сценария, затрагивающих wheel reset, tire size combobox и оба footer, прошли в каждом из четырех viewport (16/16).

Оставшиеся E2E проблемы, которые требуют решения по контракту/продукту: scroll restoration/lock и focus при мобильных drawers, CSS переполнение длинного заголовка на tablet/desktop, CTA формы брендирования, проверки mobile disclosure и селекторов, содержание Shop/supplier proof/vehicles в CI fixture, несоответствие теста для `/shop/delivery-and-returns`, а также desktop Shop navbar. Их не удаляли и не приглушали; артефакты Playwright сохранены в `test-results/` worktree. Live backend, CMS E2E, staging и production этими тестами не проверялись.

## Карта компонентов и поток данных

~~~mermaid
flowchart LR
  Admin[CMS в браузере] -->|session cookie и admin API| API[Backend API]
  API -->|SQL и транзакции| DB[(PostgreSQL)]
  API -->|загрузка, замена, удаление| S3[(S3-совместимое хранилище)]
  API -->|опубликованные read endpoints и snapshot| Public[Публичный сайт]
  DB --> API
  S3 --> API
  Admin -->|публикация сайта| Deploy[Timeweb deploy API]
  Deploy -->|сборка и статическая выкладка| Public
  Public -->|формы и корзины| API
~~~

Подтвержденная цепочка CMS:

1. Админский интерфейс в frontend-cms вызывает браузерный адаптер в src/admin/client/localStore.ts.
2. Backend принимает авторизацию и операции. Админские запросы идут через POST /v1/admin с именем операции и аргументами; отдельные endpoints обслуживают login/session/logout и загрузку/замену/удаление медиа.
3. Backend проверяет сессию, origin и доступ к операции, затем работает с PostgreSQL. Доступ к БД централизован в backend.
4. Файловые операции проходят через backend и S3-совместимое хранилище; метаданные и использования связаны с данными CMS в PostgreSQL.
5. Публичные read endpoints выбирают опубликованные записи. Сборка сайта читает snapshot и revision, генерирует статические HTML и маршруты, проверяя согласованность ревизии. После публикации может запускаться отдельный запрос на пересборку и выкладку.

Запросы к формам и корзине идут от публичного сайта в backend. Корзины основного сайта и BIZON Shop имеют отдельные типы и сессии. Внешняя интеграция Timeweb и объектное хранилище описаны исходниками и конфигурацией, но их live-доступность в этой проверке не устанавливалась.

Классификация основных наблюдений:

- **Подтвержденный дефект продукта:** сброс wheel filters переходил на базовый URL, но оставлял локальное состояние в смонтированном `WheelModelGrid`. Оба desktop/mobile reset action теперь очищают state; целевая регрессия и полный E2E проходят.
- **Подтвержденный дефект layout:** длинное русское слово не помещалось в `10ch` hero title track при `overflow-wrap: normal`. Для мобильного и узкого layout разрешен перенос `overflow-wrap: anywhere`; тест прошел на всех четырех viewport.
- **Устаревшие/неверно устроенные проверки:** помощники поиска текста не проходили через `BizonText.value`; footer тест искал строку в сериализованном HTML вместо видимого текста/ссылки; `letter-spacing: inherit` ошибочно считался hardcoded token; тесты использовали `selectOption` для custom combobox; несколько проверок ссылок и подписей ожидали прежний nav/content контракт; проверка мобильной карусели ожидала scroll-grid, тогда как `LoopedStrip` отображает один активный grid slot с transform.
- **Harness/interaction mismatch:** `.click()` Playwright прокручивал страницу к невидимой шапке до открытия drawer, после чего тест ошибочно сравнивал с позицией до клика. Scroll assertions теперь отделены от auto-scroll browser interaction; на mobile тестируется нижний link к `/shop/cart/`, а drawer остается desktop-поведением.
- **Не доказано этим публичным прогоном:** live-внешние сервисы, deployment-provider, staging и production. Локальный CMS save/publish до PostgreSQL/S3 и публичного snapshot/build подтверждены отдельным тестом ниже.

99 пропусков не интерпретируются как успешные тесты: это условные API-зависимые сценарии и проверки, ограниченные конкретными viewport-профилями. Точный список условий задается в самих тестах. CMS DB/media journey отдельно прошел 8/8, но это не покрывает все сущности и роли.

### CMS E2E и интеграции

Отдельный сценарий e2e/cms-media/media-lifecycle.spec.ts устроен как локальный сквозной harness: он ограничивает DB и S3 loopback-хостами, требует E2E в имени БД и bucket, проверяет схему и блокирует внешние запросы; сценарий должен проверять CMS login, upload, галерею, сохранение, публикацию и публичную сборку.

Первоначальный запуск остановился до тестов: backend сообщил, что не смог подтвердить готовность схемы. На тот момент Docker daemon был недоступен. Позже пользователь подтвердил, что Docker запущен; E2E был перенесен в изолированный worktree, создана отдельная временная PostgreSQL база `default_db_e2e`, восстановленная из явно тестового dump, и использован выделенный локальный MinIO bucket. Preflight подтвердил loopback DB/S3, имя тестовой базы и bucket, таблицы, ledger миграций, аккаунт и доступность хранилища. Постоянная `bizon-postgres`, staging, production и внешние сервисы не использовались.

Корневой Playwright suite тестирует публичный статический сайт. Его CI build fixture не является действующей БД и содержит минимальные записи. Несколько E2E-тестов ожидают редакционный текст, которого fixture не задает; это отдельный источник ложных падений/неполного покрытия.

## Приоритеты дальнейшей работы

1. Разблокировать изолированную CMS E2E среду: документированный baseline PostgreSQL, доступный локальный PostgreSQL и локальный S3/MinIO, аккаунт только для теста, автоматическая проверка cleanup. Повторить login → edit → save → reload → publish → snapshot/public rendering.
2. Сверить контракты и фикстуры, прежде чем менять приложение: Branding CTA, подписи/ссылки футеров, supplier proof copy, Shop hero, фильтр дисков и custom-select. Разделить продуктовые дефекты и тесты, которые проверяют старый DOM.
3. Проверить реальные потенциальные UI-регрессии: переполнение Hero, Shop hero background, scroll-lock/позиция при drawer, мобильные селекторы и доступность CTA. Для Grid/Flex записать viewport, computed gridTemplateColumns, minWidth/maxWidth и offsetWidth относительно родителя.
4. Заменять хрупкие тесты строкового HTML и неактуальные Playwright locator patterns на проверки DOM/accessibility и пользовательского результата.
5. Связать публикацию с контрольной проверкой revision и публичного результата. Unit-тест успешного dispatch не заменяет повторное чтение из БД/API и отображение опубликованной версии.

## Дополнительная CMS проверка после включения Docker

Полный `npm run test:e2e:cms-media` завершился штатно: **8 passed / 0 failed**. `npm run typecheck:e2e` прошел. Backend `npm run typecheck` прошел; после корректировки одного устаревшего ожидания backend Vitest завершился **81 файл / 399 тестов PASS**.

CMS сценарии проверили с локальным backend, PostgreSQL и S3-compatible storage: отказ от неполного PNG без записи; загрузку и байтовую целостность; выбор из библиотеки; сохранение и повторное чтение после нового входа; публикацию шины, вариантов колес, юридического PDF и главной кампании; чтение публичного API/snapshot; локальную статическую сборку и совпадение revision, SHA-256 и изображения. Проверена очистка: исходный snapshot главной восстановлен, временный asset удален, тестовый черновик не оставлен.

Три наблюдения классифицированы:

1. **Дефект backend публикации шин:** PostgreSQL возвращал SQLSTATE `42P08` из-за неявно типизируемого enum-параметра статуса в `CASE`. Исправление: явные casts к `enum_tire_models_status` и `enum_tire_variants_status` в запросах записи. Исправление перенесено в активный backend и прошло E2E, backend Vitest и typecheck.
2. **Дефект публикации колесных вариантов:** доступность каждого варианта записывалась из флага всей модели. Исправление: сохранять `variant.available !== false`, независимо от доступности модели. Исправление перенесено в активный backend и прошло E2E.
3. **Устаревшая проверка миграции:** unit-тест требовал, чтобы миграция 0039 всегда была последней, хотя добавлена миграция 0040. Исправлено ожидание регистрации миграции без предположения, что позже миграций быть не может; проверки SQL и обратной совместимости сохранены.

Первый сбой проверки картинки кампании оказался ошибкой синхронизации самого теста: он находил постоянную подсказку редактора «Черновик сохранён» до завершения запроса. Проверка теперь ожидает роль `status` и ответ `savePage`, после чего сверяет прямое API-чтение. Поведение продукта исправления не требовало. Проверки тестов не удалялись.

Основная локальная БД проверена отдельно: backend `.env` направляет на loopback `127.0.0.1:5433`, контейнер `bizon-postgres`, база `bizon`; мигратор завершился сообщением `Database schema is at 202611180040`. Повторное чтение подтвердило миграцию `202611180040`, колонку `tire_iq_articles.featured_image_alt` и enum-типы статусов шин/вариантов. Новые миграции не требовались.

Ограничение: это доказательство локальной интеграционной цепочки и локальной статической сборки; оно не доказывает работу Timeweb deploy API, staging или production. Изменения корневого public-site worktree остаются изолированными. Базовый E2E dump и локальная E2E-конфигурация не коммитились; воспроизводимый bootstrap для чистой машины остается отдельным пунктом плана.

### Очередь следующего покрытия

1. **P1 — editorial approval:** проверить editor/admin на read/edit/save/submit/approve/return и убедиться, что неподтвержденный draft не попадает в public read model.
2. **P1 — формы и заявки:** провести уникальную тестовую заявку из браузера до БД/админского списка; проверить валидацию, дубль и сетевой сбой.
3. **P1 — оставшиеся media границы:** staged replacement, media deletion с опубликованными и черновыми ссылками, S3 недоступен, cleanup после прерывания.
4. **P2 — каталог:** добавить вертикальные сценарии category/subcategory и полного product/model lifecycle; перед добавлением сравнить уже существующие unit/UI contracts.
5. **P2 — страницы и материалы:** покрыть важные public page families и материальные публикации без дублирования одного и того же общего save/publish сценария.

Это risk-based план по текущей карте кода и имеющимся тестам, не полная таблица соответствия каждой SQL-колонки и каждой public route. Подробная entity → API → table → read endpoint матрица остается открытым результатом следующего этапа.
